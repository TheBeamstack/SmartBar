# RebarConfig (SmartBar) v1.0.5 — Specification: from scheme-checker to bar-level detailer

### Placement-defect fixes (D1/D2/D3) · Track P free placement (any bar / any shape / any position, all 8 elements) · Track V validation completeness · Track S splice reach · Track O BAEL façonnage schedule · Track E interchange fidelity

> **What this release is.** v1.0.4 finished the *single-tenant product*. v1.0.5 fixes three confirmed
> placement defects and closes the gap that stops SmartBar being usable by a **rebar-detailing firm**:
> today steel can only live in a handful of pre-declared zones, with a column/beam-only, one-bar-at-a-time
> "addressable" escape hatch. v1.0.5 makes **any bar, of any shape, at any relevant position, on any of the
> 8 elements** a first-class object — as single bars, counted rows/layers, bundles, and side-face steel —
> with per-bar curtailment, faithful French-façonnage schedules, and a **lossless canonical file**.
>
> **The UI is deliberately NOT in this release.** The drawing-board / inspector / editable-canvas work is
> **v1.0.6** (`v1.0.6_spec.md`). v1.0.5 ships the *engine + data model + validation + output*, surfaced
> through the **existing** form UI (extended minimally where a new capability has no control at all). This
> keeps the two releases independently shippable and testable.
>
> **Provenance.** This spec is the synthesis of three design reviews (architecture/domain, the D1/D2/D3
> beam defects + detailing-firm gap, and the UI critique) plus the owner design decisions taken 2026-07-09
> (recorded in §8). **Companion:** `v1.0.5_owner_tasks.md` — every input only the owner / nominated
> structural engineer can provide; items that depend on one are tagged **`[OWNER-DEP → owner_tasks §X]`**.

## 0. Goal, scope & invariants

### 0.1 The goal this spec completes
Three failures, one arc:
1. **The default beam draws wrong steel.** Top bars render only over the left support; the right chapeau
   appears only when the addressable path is tripped (defects **D1/D2**). → **Part I**.
2. **A control does nothing.** "Fraction anchored at support" (`continuedToSupport`) only nudges one WARN
   band at 0.25 and never touches geometry or the schedule (defect **D3**). → **Part I**.
3. **You can't detail freely.** Steel is bound to blessed zones; the escape hatch is column/beam-only,
   one bar at a time, entered as raw section-frame millimetres. A firm cannot draw a second bottom layer,
   a side-face skin row, a bundle, or a bar at an arbitrary level on a slab/pile/stair. → **Tracks P/V/S/O**.

**North star:** *what is drawn == what is validated == what is scheduled == what is saved*, for **every**
bar the user can place, on **every** element.

### 0.2 Scope
**IN:**
- **Part I** — defect fixes D1/D2 (single placement path) + D3 (per-bar curtailment replaces the fraction).
- **Track P** — the free-placement model: a first-class placed-bar unit (single / row / layer / bundle /
  skin), **element-appropriate** on all 8 element types.
- **Track V** — validation completeness for every new kind of steel (bundle, skin, multi-layer,
  curtailment/anchorage), with the honest **🔴-block / 🟠-warn** split.
- **Track S** — lap/coupler splicing extended to **pile cages + any user-placed free bar** (not slab/mesh
  distribution steel this release).
- **Track O** — the bar-bending schedule + shop drawing in the **BAEL / French façonnage** convention,
  including a shape-code map.
- **Track E** — **lossless interchange**: the per-bar list becomes the canonical persisted unit, and the
  seismic regime + code pack are written into the canonical `.rcfg` arrays (with migration + version bump).

**OUT (explicit):**
- **The drawing-board UI** (section/elevation canvases, inspector, tool palette, drag editing) → **v1.0.6**.
- New element *types* and new code *rule-sets* beyond BAEL/EC2/RPS wiring (roadmap Track G — later).
- Accounts / cloud / IFC / building-model (Track H — later).
- Slab/mesh distribution-steel splicing (kept in stock lengths this release).

### 0.3 Hard invariants (carried from all prior specs — do not violate)
1. **Engine purity.** Nothing in `packages/core` imports React/three/DOM. New placement/validation lives
   in core; UI plumbing lives in `apps/web`. Enforced by `check:purity`.
2. **Determinism.** Pure functions; same input → identical output. No `Date.now()`/`Math.random()` in core.
3. **Everything structural is DATA.** A new shape/row-type/bundle rule is a manifest + a registered
   generator/predicate, **never** `if (elementType===…)` / `if (codePack===…)` in core. New engineering
   *conventions* (attribution, orientation factors) go behind the `CodePack`/overlay surface, not inline.
4. **SI internally, convert at the edge.**
5. **Code-pack agnosticism.** BAEL↔EC2 stays a numbers-swap behind the same `code.*` names.
6. **Forward-compat persistence (NORMATIVE).** Unknown fields / unknown `ReinforcingElement.kind`s survive
   round-trip. Track E *tightens fidelity* without weakening this.
7. **Every phase ends green.** `npm run check` (purity → manifests → typecheck → web typecheck → tests) +
   coverage ≥ 90% on solver+validation. New goldens are re-baselined **intentionally and noted** (see P1).

### 0.4 Cross-cutting quality bar (every item ships with all of these)
- Core-level pure logic + unit tests (contract/golden/reference-case) **and** the adapter/store path tested
  headlessly. A capability is "done" only if it survives **core → solve → adapter → store → (existing UI
  control) → 3D + coupe → BBS + DXF + PDF → `.rcfg` round-trip** — the same end-to-end chain the reviews used.
- Legacy docs remain **byte-identical** unless the item explicitly re-baselines a golden (P1 does; it is
  the only intentional geometry re-baseline in this release, and it is called out per test).
- Every new numeric limit is sourced (§0.5); every new WARN band is flagged provisional (§0.5, G-TOL).

### 0.5 The data spine — sourced values, honest provisional policy `[OWNER-DEP → owner_tasks §B/§C]`
Owner ruling 2026-07-09, clarified: **there are two buckets and they are handled differently.**
- **Bucket 1 — published values (transcribe + flag).** Constants that BAEL/EC2/RPS publish *with* their
  values (cover tables, min-steel ratios, lap coefficients, **bundle equivalent-Ø `φₙ = φ·√nᵦ ≤ 55 mm`,
  max 4 bars / 3 at a lap**, EC2 §8.9; **side-face/skin minimum**, EC2 §7.3.3 / §9.2.4 & BAEL; multi-layer
  clear spacing). These are **transcribed from the standard, shipped active**, and flagged for the **same
  engineer sign-off** as the existing packs (`_provisional`, G-BAEL/G-EC2/G-RPS). *Provisional here = not
  yet ratified, not "unknown."*
- **Bucket 2 — values the standard does NOT give (amber tolerance bands, geometric approximations).** The
  standard gives a *limit*, not "how near is near." Per owner ruling, v1.0.5 **DOES ship amber
  tolerance bands with default widths**, all flagged provisional under **G-TOL** — the band widths are a
  ratification item. *(Contrast the F1 lesson: a band must never make an at-limit, code-compliant design
  the FIRST thing a user sees turn amber — so a band's default is "at/above the code value = 🟢", the amber
  zone sits **below** the code value where the design is genuinely near/under the limit, never above it.)*
- **The BAEL / French façonnage nomenclature** (shape-code table, cadre/étrier/chapeau naming) is a
  **labelling convention, not structural** → **owner-supplied** (`owner_tasks §O-1`). The engine owns the
  geometry/cutLength; the owner owns what each shape is *called* on the schedule.

No new sign-off *gate types* are introduced; the existing **G-BAEL / G-EC2 / G-RPS / G-COUPE / G-TOL** cover
everything here (bundle/skin limits → G-BAEL/EC2; tolerance bands → G-TOL; façonnage codes → owner deliverable).

# PART I — Defect fixes (D1 / D2 / D3)

*These are correctness fixes and ship first; the rest of the release builds on the single placement path.*

## P1 — Unify the placement path (fixes D1 + D2)  `[REF-SYS-950 / place.ts]`
**Defect.** In the grouped (default) render path, `placeBars` maps **every** top-face bar to
`topLong = longGroups[1]` (`place.ts:190,197`) — for a two-chapeau beam that is the LEFT chapeau (`CHAPEAU`,
`params.L = extension`, forced `axisStart = 0`), so top steel renders only over the left half and the right
chapeau group is never placed (**D1**). Any override/extra trips the `longBars[]` path, whose
`buildLongBars` seats the under-filled right chapeau at its true station (`element.ts:415-430`), so the right
half appears only as a side effect of the addressable panel (**D2**). Two paths, two different beams.

**Requirement.**
- Retire the grouped placement fast-path **for any element whose faces carry more than one longitudinal
  zone** (any beam with distinct L/R chapeaux; any element with relevés / montage + chapeau on one face).
  For those, `solveElement` **always** emits `longBars[]` (drop the `overrides.length===0 && extra.length===0
  → undefined` short-circuit at `element.ts:347` *for the multi-zone-per-face case only*).
- Single-zone-per-face elements (a plain column, a slab main mat) keep the grouped fast path → byte-identical.
- `placeBars` renders from `longBars` when present (already true, `place.ts:176`); the grouped branch remains
  only for the single-path case.
- **Decouple placement from addressable-*validation* activation (audit A2).** Today the same
  `longBars !== undefined` flag gates the A2 As/`d` reconciliation (`element.ts:596`), the
  `placedCount`/`face_min_bars` path (`:663`), `validateAddressableBars` (`:818`) **and** the `richestStation`
  default coupe (`sectionAt.ts:446`). Forcing `longBars` for placement must NOT silently switch those on. Add
  an explicit **`hasUserAddressableContent`** predicate (true only for real user overrides / extras / rows) and
  gate the reconciliation + addressable validity + `richestStation` on **it**, not on the bare presence of
  `longBars`. A default multi-zone beam then gets correct *placement* while its *validation list* and *default
  coupe* are unchanged.

**Consequence (enumerated).** With the decoupling in place:
- **Moves (intentional, annotated `# v1.0.5 P1: two-support placement`):** only the beam render/placement
  goldens — the right chapeau is now drawn over its support.
- **Holds:** the BBS/schedule goldens (identical bars still merge, `bbs.ts:227`); the validation-list goldens
  (reconciliation + addressable predicates stay gated on real user content); the default coupe station
  (`richestStation` stays gated); every single-zone-per-face element (column, slab main mat) is byte-identical.

**Tests.** `tests/beam_two_support_placement.spec.ts` — a default beam renders top steel over **both**
supports at correct stations with no override present; grouped single-zone-per-face elements stay
byte-identical; a beam with + without an override renders the **same** top steel (the two-path divergence is
gone).

## P2 — Per-bar curtailment + "runs-through-to-support" (fixes D3)  `[REF-SYS-260 / profiles.ts]`
**Defect.** `continuedToSupport` (`BeamDoc.span.continuedToSupport`, 0–1) feeds only `end_support_anchorage`
with an `END_SUPPORT_FRACTION = 0.25` threshold (`profiles.ts:216,392-395`): every value in (0.25, 1] is
inert, and it never affects geometry, count, length, or the BBS. Bottom bars always render full-length.

**Requirement.**
- **Remove** the `continuedToSupport` scalar. Replace with **per-bar extent**: each longitudinal bar carries
  an explicit **start station** and **end station** (curtailment) and a per-end **anchorage choice**
  (`none | straight | hook` with code-default length, override allowed).
- **Sequencing (audit A1 — resolves the M1↔M2 cycle).** The *minimal* per-bar `start`/`end` station +
  anchorage fields land in **M1** — a small extension of the existing `axisStart` (`element.ts:122`) + the
  unique-`length` inversion (`solveDoc.applyUniqueLength`). The full `PlacedBar` model (P-A) **generalises**
  these same fields in M2; P2 does **not** depend on rows / bundles / layers, so it ships correctly in the
  defect phase.
- A **"runs through to support"** decision is the discrete case: a bar whose end station reaches the support
  face + its anchorage length. The `end_support_anchorage` check (§7.7: ≥ 0.25·As,span carried past the
  support) now counts the **bars that actually run through** (real geometry), not a fraction — and a bar
  that stops short is genuinely shorter in the drawing + the BBS cut length.
- **Migration:** a legacy `continuedToSupport = f` maps to "the `round(f · nBottom)` innermost bars run
  through to both supports; the rest curtail at the code curtailment point" — lossless, idempotent, at the
  `rcfgToDoc` chokepoint.

**Tests.** `tests/curtailment.spec.ts` — a curtailed bar is shorter in placement + BBS; "runs-through" bars
drive `end_support_anchorage` from real geometry; legacy `continuedToSupport` migrates to the equivalent
per-bar set; removing the fraction leaves no dead control.

# PART II — Track P: the free-placement model (any bar / any shape / any position)

*The core unlock. Owner decisions 2026-07-09: **all 8 elements, element-appropriate**; capabilities =
**counted rows + multiple layers + bundles + side-face skin**; curtailment = per-bar stations.*

## P-A — The placed-bar data model (first-class, canonical)  `[REF-DATA-530]`
**Requirement.** Generalise today's `LongBarOverride` / `ExtraLongBar` (`pipeline/element.ts`) and the
web-side `BarOverrideEdit` / `AddressableBar` (`document.ts`) into ONE first-class **`PlacedBar`** family
that is the persisted, canonical unit for user-detailed steel:
- **`SingleBar`** — one bar: section position `(u,v)`, shape archetype + params, Ø, start/end stations
  (P2 curtailment), per-end anchorage/hook, optional splices/autoSplice, `removed`.
- **`BarRow`** — a counted/spaced **row** placed as one object (P-C).
- **`Bundle`** — 2–4 bars in contact at one position (P-E).
- **`Layer`** — a flexural layer descriptor (P-D) attaching to a face.
Each carries a **stable id** (binding stays index/id-based, D-P3-4 — never coordinates). The engine emits a
resolved `PlacedBar[]` that `placeBars` + `computeBBS` + `sectionAt` consume (they already read `longBars`;
this widens that channel). **No `if(elementType)`** — placement semantics come from the section descriptor
(P-B), not element branching.

**Note.** This subsumes P1's "always emit for multi-zone-per-face" — once the placed-bar list is the single
long-steel truth, the grouped path is a *compression* the BBS reverses, not a second geometry source.

## P-B — Element-appropriate free placement on all 8 elements  `[REF-SYS-530]`
**Defect.** The four generic orchestrators (`pipeline/{circular,slab,stair,joist}.ts`) have **no** per-bar
channel; slab bars are per-metre span stations, circular bars sit on a pitch circle. Free placement is
column/beam-only today.

**Requirement — a shared post-layout placement pass, wired into every pipeline**, with section-appropriate
semantics (owner: "all 8, element-appropriate"):
- **RECT (column, beam):** a free bar is `(u,v)` + shape + start/end station — snapped to the cover envelope
  + a layer grid (grid def is UI, 1.0.6; the model accepts any `(u,v)`).
- **SLAB / JOIST:** a free "bar" is an **extra band** at a level (`v`) over a span range, expressed as a row
  (P-C) with a spacing or count across the width — e.g. an extra top band around a support. The per-metre
  provided-area accounting (`slabProvidedPerMetre`) gains these bands.
- **CIRCULAR (spiral column, pile):** a free bar is a **pitch-circle addition** (extra bar at an angular
  position) **or** a free interior `(u,v)` bar (e.g. a bundle at the centre of a large pile). The
  `EQUAL_PERIMETER` layout gains an "extra bars" set outside the primary count.
- **STAIR:** free bars ride the waist/landing frame like the main bar (the `MARCHE_PALIER` mapping already
  exists) at a chosen `(u,v)`.

**Implementation shape.** Extract the `buildLongBars` reconstruction (`element.ts:339`) into a shared
`resolvePlacedBars(section, layout, placed[], code)` in `packages/core/section/` (or `layout/`), called by
`solveElement` **and** the four generic shims. Each shim passes its section descriptor + its native layout
bars; the pass appends the resolved `PlacedBar[]` to the `SolveResult`. The generic shims gain
`placed?: PlacedBarInput[]` on their `*SolveInput`.

**Two placement modes, different section-sensitivity (audit B3).** *Free / row / bundle* placement at a chosen
`(u,v)` (or a slab band / circular angular position) is **section-agnostic** — it resolves the same everywhere.
A *per-bar override onto an existing layout bar* is **section-aware**: it maps by the section's own bar
convention — RECT by the `TOP/BOTTOM/LEFT/RIGHT` face + zone distribution (`element.ts:361–381`), SLAB/JOIST by
`faceTag = zone` (the `byZone` branch already exists, `element.ts:373`), CIRCULAR by pitch-circle index (`CIRC`).
The shared pass therefore carries a small **section-specific bar/face resolver** used only for the override case;
the free-placement path needs no per-section logic.

**Tests.** `tests/placed_bars_all_elements.spec.ts` — a free bar renders + schedules + appears in the coupe
for each of the 8 elements; legacy docs (no placed bars) are byte-identical per element.

## P-C — Counted / spaced rows (a layer in one entry)
**Requirement.** A **`BarRow`** places N bars in one object: an anchor `(u,v)`, a direction, and either a
**count** or a **spacing** across a span, one shape/Ø/curtailment for all. One entry = a whole row (a 2nd
bottom layer, a mid-depth skin row, a top band). It resolves to N `SingleBar`s at solve time (so 3D/coupe/BBS
see real bars) but is edited/persisted as one object. Feeds As,prov (P-A weighted reconciliation,
`element.ts:572`) and clear-spacing (Track V).

**Tests.** `tests/bar_row.spec.ts` — a row of 4 resolves to 4 scheduled bars; count↔spacing equivalence;
As,prov includes the row.

## P-D — Multiple flexural layers  `[REF-SYS-611]`
**Requirement.** Explicit 2nd/3rd layers of bottom or top steel with a **layer spacing**, attaching to a face.
The rect layout already reserves `RectLayout.layers` (`placement.ts:21`) — activate it: a layer offsets `v`
by `(Ø + layerGap)` per layer. Layers feed the **area-weighted effective depth `d`** (`computeZoneGeometryWeighted`,
`layout/rect.ts`) — a lower second layer correctly lowers `d`. Clear spacing checked **within and between**
layers (Track V-D).

**Tests.** `tests/layers.spec.ts` — a 2-layer bottom lowers `d` vs 1 layer (exact, area-weighted); between-layer
vertical clear spacing checked; single-layer byte-identical.

## P-E — Bundled bars  `[REF-SYS-Bundle]`
**Requirement.** A **`Bundle`** = 2–4 bars in contact at one position. Effects (all sourced, Bucket 1):
- **Schedule count** = the real bar count (a triple bundle = 3 scheduled bars, one mark).
- **As,prov** = n × bar area.
- **Equivalent diameter** `φₙ = φ·√nᵦ` (≤ 55 mm) drives cover, clear-spacing-to-neighbours, and mandrel/lap
  rules (EC2 §8.9 / BAEL). Exposed as a pack extra `code.bundleEquivDiameter(φ, n)`.
- **Limits (Track V-B):** > 4 bars (or > 3 at a lap) → 🔴; a bundle where `φₙ` breaches cover/spacing → 🔴.

**Tests.** `tests/bundle.spec.ts` — count/As/φₙ; > 4 bars FAIL; bundle cover breach FAIL; lap-zone triple max.

## P-F — Side-face / skin reinforcement rows  `[REF-SYS-Skin]`
**Requirement.** Distributed longitudinal bars on beam side faces (deep beams), as a **`BarRow`** on LEFT/RIGHT
faces with a spacing. Minimum skin steel is a code requirement above a depth threshold (EC2 §7.3.3 /
§9.2.4, Bucket 1). The existing SKIN supplement fanout (`resolveSupplement`, B3) is folded into the row model
so skin bars are first-class placed bars (counted, curtailable, scheduled), not presence-only add-ons.

**Tests.** `tests/skin_steel.spec.ts` — a skin row renders/schedules on both faces; the depth-triggered
minimum check fires (🟠 if under, per Track V); As credited to the correct region.

## P-G — Coupe fidelity for every placed-bar type (audit C1)  `[REF-SYS-950 / sectionAt.ts]`
**Requirement.** The north star (drawn == scheduled) includes the **coupe**, not only the 3D + BBS. `sectionAt`
is representative for slab-family (`D-P5-3`); this item guarantees each **new** placed-bar type reads correctly
in the cross-section: a **bundle** shows n touching dots at its `(u,v)`; a **layer** shows a distinct row at its
depth; a **skin** row shows the side-face dots; a **slab band** / **circular free bar** appears at its station.
A placed bar the cut plane misses is correctly absent (the `richestStation` default already reveals offset bars,
`sectionAt.ts:446`). No new coupe *convention* is introduced (those stay G-COUPE); this is fidelity of the
existing plane∩geometry to the new bars.

**Tests.** `tests/coupe_placed_bars.spec.ts` — one case per new type (bundle / layer / skin / slab band /
circular free bar): the bar is present in the `CoupeView` at the right position when the plane crosses it, absent
when it doesn't; existing coupe goldens hold for docs without placed bars.

# PART III — Track V: validation completeness for the new steel

*Owner decision: **split — hard 🔴 block, soft 🟠 warn**; amber tolerance bands ship with default widths,
flagged **G-TOL** (§0.5, Bucket 2).*

## V-A — Extend the addressable predicates to all elements  `[predicates.ts]`
`validateAddressableBars` (`predicates.ts:85`) — axial-extent / section-bounds / clear-spacing — currently
runs on the RECT path.
- **Element-agnostic parts** (axial extent within `[0, memberLength]`; bar inside the concrete/cover envelope)
  **generalise** to every element that carries placed bars (P-B): the envelope comes from the element's own
  descriptor (RECT b×h, CIRCULAR D, SLAB width×t). A bar outside the concrete/cover envelope → 🔴; merely tight → 🟠.
- **Section-specific parts** (clear spacing) do **not** generalise as-is: a slab is judged **per metre** and a
  circular by **arc spacing**, not by the rect `(u,v)` clear-spacing metric. So the RECT clear-spacing predicate
  stays rect-only; the slab/circular spacing checks reuse the existing per-metre / arc-spacing profile checks,
  now fed the placed bars. *(A unified spacing predicate across sections is out of scope — logged for a later point release.)*
- **Affected-bar fix (W4).** FAIL-red today matches `affectedGroupIds` by **`groupId`** (`rebarProps.ts:32–36`),
  so a base-bar override reddens the whole group. `validateAddressableBars` must emit the offending bar's
  **stable placed-bar id** in `affectedGroupIds`; a standalone bar's id already flows through `placeBars`
  (`groupId = lb.groupId`), so a per-bar id lights exactly one bar. *(`rebarProps.ts:148` is the separate
  `selectedBars` selection path — not the FAIL path.)*

## V-B — Bundle rules (published)  `[Bucket 1, G-BAEL/EC2]`
Max bars per bundle (4; 3 at a lap) → 🔴 over-limit; `φₙ` cover/clear-spacing breach → 🔴; near-limit → 🟠 band.

## V-C — Side-face / skin minimum (published)  `[Bucket 1]`
Depth-triggered minimum skin area/spacing per pack; under-provision → 🟠 (judgement — expert may proceed);
absent where mandatory by depth → 🟠 with an actionable message.

## V-D — Multi-layer clear spacing + `d` (published)  `[Bucket 1]`
Vertical clear spacing between layers ≥ `max(Ø, dg+k, abs min)` → 🔴 if clashing, 🟠 if tight; `d`
recomputed area-weighted across layers (P-D).

## V-E — Curtailment / anchorage checks  `[§7.7]`
A curtailed bar must extend the code anchorage/development length past its theoretical cut-off → 🔴 if short,
🟠 if within the tolerance band; "runs-through" bars drive the real `end_support_anchorage` (P2).

## V-F — Severity policy & the tolerance-band shape
- **🔴 (blocks export):** un-buildable / code-forbidden — bar outside concrete, bundle > max, layer clash,
  anchorage grossly short.
- **🟠 (warns, stamps "À vérifier"):** near a limit / judgement — skin steel a touch low, tight-but-fittable
  spacing, curtailment within the band.
- **Tolerance bands (Bucket 2, G-TOL):** default width per rule, flagged provisional; the amber zone sits
  **below** the code value (approaching/under the limit), so an at-or-above-limit design is always 🟢 (the F1
  guarantee) `[OWNER-DEP → owner_tasks §B: G-TOL band widths]`.

**Tests.** `tests/placed_bar_validation.spec.ts` — one case per rule at 🔴 / 🟠 / 🟢; the F1 guarantee (an
exactly-at-limit design is 🟢, never 🟠) asserted for every new band; affected-bar id highlight.

# PART V — Track O: BAEL / French façonnage output

**Owner decision: BAEL / French façonnage convention** (owner supplies the nomenclature, §0.5).
- **Shape-code map** — each shape archetype → its French façonnage designation + the schedule sketch/dims
  convention, from an **owner-supplied table** (`[OWNER-DEP → owner_tasks §O-1]`). The BBS `shapeArchetypeId`
  (`bbs.ts`) is replaced on the *rendered* schedule by the façonnage code (the internal id stays the data key).
- **Schedule columns** — align to the French BBS layout (repère / nombre / Ø / longueur de coupe / façonnage
  (croquis coté) / masse), extending the existing `computeBBS` + `shopDrawing` bending table (`shopDrawing.ts`)
  which already emits mark · sketch · Ø · cut · count · total.
- **Drawing** — leader marks + façonnage table already exist (`shopDrawing.ts`, D-V103-7); this item swaps the
  code nomenclature + column headers, not the geometry.
- Bundles/rows/layers/curtailed bars all schedule correctly (real bars, merged marks) — the Track P output invariant.

# PART VI — Track E: interchange fidelity (lossless canonical file)

**Owner decision: do it fully in 1.0.5.**
- **Per-bar list becomes the canonical persisted unit — a `ReinforcingElement` CONTRACT EXTENSION (audit B4).**
  `reinforcementFromResult` (`canonical.ts`) today emits group-based `ReinforcingElement[]` and drops per-bar
  shape/splices/curtailment to the private `meta.app_document` blob (`rcfgDoc.ts:8-14`). A **bundle / row /
  layer / curtailed bar is NOT expressible** in the current `BarGroup` (`reinforcing-element.ts` — it carries a
  `distribution` + `placement`, no bundle count, no layer, no per-bar station). So this item **extends the core
  `ReinforcingElement` contract**: add a `PLACED_BAR` kind (or additive `bundle`/`layer`/`stations` fields on
  `BarGroup`), map each `PlacedBar` onto it faithfully, and make `app_document` a convenience carry, no longer
  the sole truth. **Forward-compat (NORMATIVE) is preserved AND newly tested for the new kind:** an *older*
  reader must round-trip a file containing the new `PLACED_BAR` kind without dropping it (the D-P0-2 unknown-kind
  guarantee, now exercised by our own new kind).
- **Seismic + code pack in the canonical arrays.** `docToRcfg` hardcodes `seismic: null` (`rcfgDoc.ts:77`,
  stale comment) though `SeismicControls` exists and `doc.seismic` is live. Populate `seismic` + `codePack`
  from the doc.
- **Stop the double-solve.** `docToRcfg` re-solves the doc only to fill the arrays (`rcfgDoc.ts:70`); pass the
  store's live `result` instead.
- **Migration + version bump.** Bump `rcfg_version` (additive, idempotent); a v1.2/earlier file migrates
  forward; **forward-compat invariant preserved** (unknown fields/kinds survive). `app_document` carry may
  remain as a convenience but is **no longer the sole source of truth** — the canonical arrays are lossless.

**Tests.** `tests/interchange_lossless.spec.ts` — all 8 elements round-trip **through the canonical arrays
alone** (app_document stripped) with per-bar detail + seismic + codePack intact; migration chain +
future-version pass-through + unknown-kind survival.

## 10. Definition of "complete" for v1.0.5 (audit A3 — scoped honestly)
**Engine-, model-, validation-, schedule- and file-complete, and headlessly proven end-to-end.** Concretely:
- the three defects are gone — a default beam draws correct two-support top steel, and no control is dead;
- the `PlacedBar` model can express **any bar / shape / position on any of the 8 elements** — single bars,
  rows, layers, bundles, skin — with per-bar curtailment, and each is **validated (🔴/🟠 honestly), scheduled
  (French façonnage), drawn in 3D + coupe, and saved losslessly** through the canonical file;
- every item above is proven through the full **core → solve → adapter → store → 3D/coupe → BBS/DXF/PDF →
  `.rcfg` round-trip** chain in tests.

**Explicitly NOT claimed for 1.0.5:** *full user reach*. The only existing input surface is `AddressableBars`
(column/beam, numeric, single bars). Rows / bundles / layers / skin, and free placement on the six generic
elements, are **engine-complete but only minimally reachable** through the existing form in 1.0.5 — the tool
palette + section/elevation editing that make them **operable** are **v1.0.6** (`v1.0.6_spec.md`). 1.0.5 ships
the capability + its proof; 1.0.6 ships the reach. This boundary is intentional and keeps the two releases
independently shippable.
