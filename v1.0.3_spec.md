## 0. Why this increment + the invariants it must not break

v1.0.2 shipped the seven F‑features but hands-on testing exposed that the **3D/coupe/PDF render bars as straight
axis lines** (so façonnage, hooks, relevés, the spiral coil and the stair profile never appear), the **bar model
is a flat "group of N identical bars"** (so per-bar shaping, U-bar levels, unique-length bars and laps can't be
expressed), the **beam support model is a single collapsed zone**, and the **shop drawing lacks leader lines,
marks, section/cover dimensions and a bending table**. v1.0.3 closes all of it.

**Hard invariants (do not violate).**
1. **Engine purity & data-driven (v1.0 §2, §0.1).** No React/three/DOM in `packages/core`; no new
   `if (elementType===…)` / `if (codePack===…)`. New geometry = registered shape generators + placement data.
2. **Determinism.** Pure solver, byte-identical output for a given input.
3. **`cutLength` invariant (D-P1-1).** Every bar (full-length, unique-length, spliced segment, relevé, hook)
   keeps `cutLength = Σ legs + Σ hookExt − Σ bendDeduction`, cross-checked vs `totalLengthExpr`.
4. **`.rcfg` forward-compat (NORMATIVE, v1.0 §10).** All new persisted data — addressable bar overrides,
   section levels, independent/unique-length bars, beam supports, relevés, lap splices, drawing marks — is
   **additive**; a v1.0.2 file loads via legacy defaults (one level = today's faces, no overrides, one support).
5. **a11y parity.** Every new pointer action (section-picker slot click, hand-pan, lap-point drag) has a
   keyboard/numeric equivalent.
6. **Golden discipline.** Renderer/exporter goldens that legitimately change (the elevation now draws bent
   bars; the coupe now has dims) are **re-baselined intentionally** and called out; the BBS/cutLength goldens
   stay byte-identical (cut lengths are unchanged by *rendering*).
7. **Engineering gates.** Lap/coupler lengths (G4) and support anchorage (G3) call `code.*` (`l0`/`lbd`) — they
   **ride the existing provisional BAEL/EC2 packs** (G-BAEL/G-EC2); no new sign-off gate, constants flagged
   `_provisional` as today.

## 1. G1 — True bar geometry rendering  [REF-SYS-960]

### 1.1 The defect
`placeBars` (core — the single geometry source for the 3D viewport, the Section/Coupe engine and the PDF/DXF
elevation) draws every **longitudinal bar as a straight axis line** `[u,0,v → u,L,v]`, ignoring the group's real
bent `centerline3D`; and it **instances transverse loops per station**, so a continuous **spiral coil is
replicated at every station and flattened** by `placeLoop`. Consequence: façonnage/hooks/relevés never render,
endpoints never exit the concrete, and circular/pile cages are a tangle.

### 1.2 Behaviour  [OWNER ✓ true geometry, all elements]
- **Longitudinal & distribution bars render their real `centerline3D`**, oriented along the member axis at the
  bar's section position `(u,v)`. A straight bar is unchanged; a hooked/cranked/relevé/stair-waist bar shows its
  true shape, and **its bent endpoints visibly exit the concrete envelope** (G8).
- **Continuous coils (spiral/helix) are placed ONCE** as a single member-length helix (detected via the shape's
  `coilLength`, as the BBS already does) — never instanced per station, never flattened.
- **Stair main bars follow the waist+landing profile** (the `MARCHE_PALIER` bend), so the cage reads as a stair
  (with G8's stepped concrete).
- **Hoops/cadres/stirrups/épingles** keep the per-station loop instancing (correct for discrete sets), but
  épingles are now **anchored** (G5) and their **hooks are part of the rendered centreline** (G5/§1).

### 1.3 Engine impact (core, within the placement seam)
- `placeBars` gains: (a) for longitudinal bars, emit the group's `centerline3D` translated/oriented to the bar's
  `(u,v)` and member axis (instead of the straight 2-point line); (b) a **continuous-coil branch** that places
  the helix once along the axis using its true 3D centreline; (c) honour the §5 cadence (G6) for stations.
- Because the **elevation fiche + coupe consume `placeBars`**, true geometry flows to PDF/DXF for free.
- **Goldens:** the elevation DXF/PDF goldens (`dxf1_golden`, fiche-derived) re-baseline (bars are now bent);
  BBS/cutLength goldens unchanged. Performance: the densest cages must stay < 16 ms (perf test extended).

### 1.4 Acceptance
- A façonné/hooked/relevé bar renders its true shape in 3D, the coupe and the PDF/DXF elevation, with endpoints
  exiting the concrete; a spiral renders as one clean coil; a stair reads as a stair.
- `npm run check` green (re-baselined render goldens called out); perf < 16 ms on the heavy cases.

## 2. G2 — Addressable bars, section levels & the façonnage editor (L2)  [REF-DATA-530 / REF-UI-530 / REF-SYS-530]

### 2.1 Intent
Move from "a group = N identical bars" to **individually addressable bars** so the user can shape one bar, add
an independent bar, replace a bar, give a bar a unique length, and place bars on **multiple section levels**.

### 2.2 Section levels  [OWNER ✓ explicit levels incl. an intermediate U-bar level]
The cross-section gains **named depth levels** (vertical bands), not just the BOTTOM/TOP faces:
- A beam ships levels **BOTTOM** (span steel), **TOP** (montage/chapeaux) and an **intermediate level** (e.g.
  *sous-chapeau* — the U-bars over supports sit just under the top bars, as in the reference drawing). The model
  allows **N user levels** between bottom and top, each at a settable depth `v`.
- A column keeps its four faces; "level" maps to the existing `LAYERED` layer index (concentric layers).
- Each bar/zone declares the **level** it occupies; the layout solver places it at that level's `v` and the
  effective-depth `d` reads the real centroid (unchanged math, D-P1-5).

### 2.3 The addressable-bar model  [OWNER ✓ L2]
- A reinforcement group still has a **count** (the common case), but each member bar is **addressable** and may
  carry an **override**: a different `shapeId` + `faconnage` (params + per-end hooks), a **unique length** +
  **axial position**, a different diameter, or **replace/remove**.
- The user can **add independent bars**: a standalone bar with its own level, section position, shape, length
  and axial position — not part of any count-group.
- **Façonnage applies per bar** (one chosen bar, at one *or* both ends) — not only per group (closing the v1.0.2
  per-group limitation).

### 2.4 Placement & the editor  [OWNER ✓ picker + numeric; abs length + axial position]
- **Position:** pick a bar/slot on the **2D section picker** (reuses F7, now level-aware) **AND** numeric fields
  (face/level + offset). Both paths write the same data (a11y parity).
- **Unique length:** **absolute length (mm) + axial position** along the element (e.g. a 1.50 m bar starting at
  the left support) — matches the `l=1.50` marks in the reference drawing.
- **Façonnage editor (completing v1.0.2 F6):** the editor now (a) targets a **specific bar** (or the group), (b)
  flows to 3D/coupe/BBS/DXF/PDF via G1 (the v1.0.2 gap), (c) keeps the live sketch + cutLength guard (D-P1-1),
  (d) supports the new shapes already shipped (Z/double-crank/stepped) + the catalog.

### 2.5 Engine / data impact
- Doc model: a group gains an optional **`barOverrides: { index, shapeId?, faconnage?, length?, axialPos?,
  diameter?, removed? }[]`** and the doc gains an **`extraBars: AddressableBar[]`** list + a **`levels`**
  declaration. All **additive**; absent → today's behaviour (legacy byte-identical).
- The adapter (`solveDoc`) expands a group into per-bar engine inputs only when overrides/levels/extra bars are
  present (else one grouped input — goldens safe). **Engine stays generic**: it already accepts arbitrary
  shapes/params/positions; levels feed the existing layout `v`/`layerIndex`.
- **BBS:** distinct bars still merge by shape+Ø+dims (so identical bars share a mark); a unique-length or
  uniquely-shaped bar becomes its own line. `.rcfg` round-trips the overrides/levels/extra bars.

### 2.6 Acceptance
- A user can: shape a single bar (one/both ends), add an independent bar, replace/remove a bar, give a bar a
  unique length + axial position, and assign bars to ≥3 section levels — all visible in 3D/coupe/PDF/DXF + the
  schedule. Legacy files load unchanged. `npm run check` green.

## 3. G3 — Beam two-support model + relevés  [REF-DATA-260 / REF-SYS-260]

### 3.1 Intent
A real beam has **two distinct supports** with their own steel; the reference drawing shows asymmetric chapeaux
(`l=1.50` left, `l=1.55` right) and a bent-up **relevé** (`3Ø10 l=5.40`). Today the beam is one representative
support.

### 3.2 Model  [OWNER ✓ two supports V1/V2 · relevés first-class · auto-seed editable stirrup regions]
- **Two supports V1 / V2**, each with: its own **chapeau** zone (length, Ø, count), **bottom-bar anchorage
  length** into the support, and a **support width** (bearing). Supports may be **asymmetric**.
- **Relevés** become a **first-class beam zone**: a bottom bar bent up near a support (the `RELEVE` shape) with
  its own count/Ø and bend stations, placed + shown in 3D/coupe + scheduled (a unique-length, shaped bar — rides
  G2).
- **Support → stirrups:** defining a support zone **auto-seeds the F5 stirrup regions** (a tighter end-region at
  each support + a looser middle — the `11×9 / 15×20 / 11×9` pattern), which the user can then **edit** (G6).
- **Drawing (G7):** label **V1/V2**, dimension **support widths/bearing**, and show **bottom-bar anchorage** into
  each support.

### 3.3 Engine impact
- The beam adapter (`solveDoc.beamInput`) builds **per-support** chapeau + anchorage + relevé inputs (still the
  generic `solveElement`; no core branch). The `BAEL_BEAM`/`EC2` profile validates each support's anchorage +
  chapeau curtailment via `code.*` (existing `computeCurtailment`, now per support). Asymmetry is data.
- `.rcfg`: supports/relevés are additive; a legacy single-`supportZone` file migrates to **symmetric V1=V2** +
  no relevé.

### 3.4 Acceptance
- A beam can have asymmetric V1/V2 chapeaux + anchorages + widths, a relevé zone, and auto-seeded editable
  stirrup regions; all render + schedule + annotate on the drawing. Legacy beams migrate. `npm run check` green.

## 4. G4 — Lap splices / couplers (full scheduling)  [REF-SYS-770 / REF-DATA-770]

### 4.1 Intent  [OWNER ✓ full lap/coupler scheduling]
A long bar is fabricated in **spliced segments** (stock-length limited) or joined by **couplers**. v1.0.3 models
laps + couplers fully: the splice geometry, the **lap length** (code), **stagger**, and the schedule effect
(each segment is its own scheduled bar).

### 4.2 Model
- A longitudinal bar/group may declare **splice points** along its length (manual, or auto when the run exceeds
  a stock length — default 12 m, reuses the BBS `nestCuts` stock). Each splice is a **lap** (overlap length
  `l_r` from `code.l0(...)`) or a **coupler** (mechanical, zero overlap, a coupler item).
- **Stagger:** adjacent bars' splices are offset by a code fraction so laps don't coincide in one section (a
  validation predicate: "laps staggered" — WARN if coincident in a critical zone, reuses the seismic
  `lap_in_critical_zone` seam).
- **Schedule:** a spliced bar becomes **N segment bars** (each its own cut length incl. the lap overlap) + a
  **coupler count**; the drawing shows the **splice symbol + lap length** at each splice; the bending table lists
  the segments.

### 4.3 Engine impact
- Pure core: a `spliceBar(centreline, splices, code) → segments[]` helper (lengths incl. `l0` overlap, cutLength
  invariant preserved). Lap length from the existing pack `code.l0`/`lbd` (provisional → G-BAEL/G-EC2).
- BBS/exporters consume the segments; `.rcfg` persists splice points (additive; absent → unspliced).

### 4.4 Acceptance
- A bar can be spliced (lap or coupler), staggered, with the lap length from the active pack; segments + couplers
  appear in the schedule + drawing; a coincident-lap-in-critical-zone WARNs. Legacy bars are unspliced.
  `npm run check` green.

## 5. G5 — Cross-tie / épingle unification + anchoring  [REF-SYS-756b]

### 5.1 Behaviour  [OWNER ✓ zero by default · all anchored · hooks visible · legacy path removed]
- **Default elements ship with ZERO épingles** (no phantom mid-length épingle).
- **Every épingle is anchored** ON the line between the two bars it engages — in 3D, the coupe and PDF/DXF —
  **never centred**. Its **hook (angle de crochet) is rendered** at the user's angle (the épingle's `hook_angle`
  already drives the geometry — G1 makes it visible; the coupe draws the **true bent hook**, §6).
- **The legacy "supplement épingle" centred path is removed** — *all* épingles (and any U-bar-style ties) go
  through the **one F2 cross-tie model** (anchored, bar-pair-bound). Supplements that were épingles migrate to
  cross-ties.

### 5.2 Engine impact
- `placeBars`: delete the centred-supplement fallback for épingle-role groups; route them through the anchored
  path (G1). The web adapter folds legacy supplement-épingles into `crossTies` at the `rcfgToDoc` chokepoint
  (additive migration, idempotent).

### 5.3 Acceptance
- No default épingle; every épingle sits between its bars with a visible hook in 3D + coupe + PDF/DXF; no centred
  épingle remains anywhere; legacy supplement-épingles migrate. `npm run check` green.

## 6. G6 — Per-zone stirrup cadence continuity  [REF-SYS-757b]

### 6.1 Behaviour  [OWNER ✓ continue from the last cadre]
When a new spacing **region** starts, its first cadre is placed **one new-spacing step after the last placed
cadre of the previous region** — not at the region's `from` station. The region `from` only marks **where the
new spacing takes over**; this removes the illogical short gap at a boundary (e.g. a 2 cm stub).

### 6.2 Engine impact
- `regionStations` (core, place.ts) changes from "restart at `r.from`" to "**carry the running station across
  the boundary**, switching the step to the new region's spacing once past `from`". The single-full-length
  region path stays byte-identical (goldens safe); BBS per-region counts + the elevation callouts follow.

### 6.3 Acceptance
- Across a region boundary the cadre cadence is continuous (no short stub); uniform sets unchanged; BBS counts +
  elevation callouts reflect the corrected stations. `npm run check` green.

### 6.4 Coupe section dimensions + cover  [OWNER ✓ section dims + cover both faces]  [REF-SYS-925c]
The PDF coupe (`drawCoupe` in `pdf.ts`) must render the `CoupeView.dimensions` it currently ignores: the
**overall width × height** of the section **and the enrobage (cover) dimension** from the concrete face to the
bars **on each face** (the DXF coupe already draws `view.dimensions`; the cover dimension is added to the
`CoupeView` for both). The elevation gains **region-length dimension lines** (not just total length) under the
stirrup-zone callouts.

## 7. G7 — Shop-drawing PDF/DXF  [REF-SYS-930]

### 7.1 Intent
Make the exported PDF/DXF a proper reinforcement shop drawing matching the reference beam image — not a bare
projection + plain table.

### 7.2 Content  [OWNER ✓ all four annotation groups · per-element sequential marks · merged bending table]
On the elevation + a per-element table:
1. **Per-bar leader lines** — a pointer from each distinct bar run to a label **`mark · nØd · l=length`** (e.g.
   `① 3Ø12 l=1.50`).
2. **Per-element sequential bar marks** (repères **1,2,3…**) on the drawing; the **project-wide schedule still
   namespaces** by element mark (`P1-…`, v1.0.1) — both coexist.
3. **Coupe markers (A-A, B-B…)** — the cutting-line symbols + tags positioning each cross-section (extends the
   v1.0.1 `cuttingLineFiche`).
4. **Stirrup-zone annotations** — the `count × spacing` notation per region (`11×9`, `15×20`) under the
   elevation (from G6's region stations).
5. **Support labels + dimensions** — `V1`/`V2`, support widths/bearing, bottom-bar anchorage (G3).
6. A **façonnage / bar-bending table** — **one row per distinct shape** (mark · shape sketch · Ø · cut length ·
   **count per element** · **total = count × element quantity**), like a standard BBS + the reference drawing.

### 7.3 Engine impact
- The annotation model is built **once** (an exporter `shopDrawing(result, marks)` layer over the existing
  `buildElevationFiche` + `computeBBS` + `sectionAt`), shared by PDF + DXF so they agree. A **leader-line
  placement** helper (anti-overlap, the v1.0 §9.2 collision note finally actioned at a basic level). The
  bending-table sketch reuses the `fiche` (legs/bends/hooks) per scheduled shape.
- Pure/deterministic; goldens for the new annotations added.

### 7.4 Acceptance
- The PDF/DXF show leader-lined bars with sequential marks + `nØd · l=`, coupe markers, stirrup-zone notation,
  support labels/dims, and a per-distinct-shape bending table with per-element + total counts. Deterministic
  with a fixed date. `npm run check` green.

## 8. G8 — 3D fidelity (concrete + stair)  [REF-UI-840]

### 8.1 Behaviour  [OWNER ✓ transparent + crisp edges · stepped stair concrete]
- **Concrete renders as a transparent solid with crisp outline edges** (an `Edges`/outline pass over the
  envelope) so the volume reads as a block and the bars + their exiting endpoints (G1) are clearly legible —
  fixing the "half-empty" look.
- **Stair concrete is a stepped profile** (risers/goings) over the inclined waist (not a flat slab), so the 3D
  reads as a real stair (pairs with G1's bent stair bars).

### 8.2 Engine impact
- Viewport-only (`Viewport.tsx`): add the concrete edge pass; build the stepped stair mesh from the stair
  geometry (`g`, `r`, `n_steps`, `waist_t`) — the geometry params already exist on the solve. No engine change.

### 8.3 Acceptance
- Concrete reads as a clean transparent solid with edges; bent endpoints visibly exit; the stair shows steps.
  Owner GPU-verifies. `build:web` green.

## 9. G9 — Camera fixes: roll, ViewCube, hand/pan  [REF-UI-811b / REF-UI-850]

### 9.1 ViewCube auto-rotation + roll  [OWNER ✓ fix auto-spin · roll auto-levels on orbit]
The F1 `RollController` mutates `camera.up` + `lookAt` **every frame** at `useFrame` priority 1; with
`OrbitControls enableDamping` this **precesses/auto-spins** (and the positive render priority can hijack the
loop). Fix:
- Apply roll **only as a discrete, on-demand transform** (on the roll button/slider), not a perpetual per-frame
  mutation; drop the priority-1 frame loop.
- **Roll auto-levels when the user orbits** (starting an orbit/drag resets roll to 0) — removes the up-vector
  conflict; the cube stops auto-rotating.

### 9.2 Hand / pan tool  [OWNER ✓ toolbar hand toggle]
A **hand-tool toggle** in the viewport toolbar: when active, **left-drag pans** the model (focus on a part);
toggle off (or pick orbit) to return to rotate. Zoom always works; the existing modifier-pan stays. a11y: the
toggle is a button; pan has keyboard arrows as the no-pointer path.

### 9.3 Acceptance
- The ViewCube no longer auto-rotates; roll works on demand + auto-levels on orbit; a hand toggle pans on
  left-drag and restores orbit. View/roll/pan state stays **session-only** (not in `.rcfg`). `build:web` green.

## 10. Cross-cutting & sequencing

- **Build order (suggested):** **G1** (true geometry — unblocks the visual half of everything) → **G6** (cadence
  + coupe dims, small) → **G5** (épingle unification, depends on G1) → **G2** (addressable bars + levels — the
  big model change) → **G3** (beam supports + relevés, depends on G2) → **G4** (laps, depends on G2) → **G7**
  (shop drawing, depends on G2/G3/G4 marks) → **G8 + G9** (GPU fidelity + camera, owner-verified).
- **Engine vs UI:** G1/G2/G3/G4/G5/G6 touch `packages/core` (placeBars, layout levels, splice helper, region
  cadence, profiles) — all via existing seams, headless-testable. G7 is exporter. G8/G9 are viewport (GPU).
- **No new sign-off gate** — G3 anchorage + G4 laps ride the provisional BAEL/EC2 packs (G-BAEL/G-EC2).
- **Tests to add:** `true_geometry`/`coil_placement`/`stair_bars` (G1), `bar_overrides`/`section_levels`/
  `independent_bars` (G2), `beam_supports`/`releve` (G3), `lap_splice`/`coupler`/`lap_stagger` (G4),
  `epingle_anchored` (G5), `region_cadence`/`coupe_dims` (G6), `shop_drawing`/`bar_marks`/`bending_table` (G7),
  plus re-baselined elevation render goldens, all green.
