# RebarConfig v1.0 — Production Software Specification
### Web-Based Parametric Structural Detailing Platform

**Status:** Buildable specification (v1.0 scope frozen) — **revision r3** (r2 contracts retained; r3 adds the **engineering-correctness pass**: computed effective depth `d` (§6.1), leg-counted transverse area `Asw` (§7.5), anchorage/lap refinements — `As,req/As,prov` reduction + automatic bond-condition classification (§7.7), bar **curtailment / shift rule** (§7.7), bend **bearing-stress mandrel** check (§7.6), EC2 minimum shear ratio (§7.5), fire & cast-against-earth cover (§7.3), and a set of **topological detailing-validity predicates** (§7.13) — seismic laps in critical zones, stair re-entrant corners, two-way-slab corner torsion, slab-distribution minima, end-support anchorage. IFC remains deferred to **v1.1**.)
**Date:** 2026-06-24
**Scaling model:** **Horizontal first.** v1.0.1, 1.0.2, … add *breadth* — new elements and new civil-engineering **design principles** (e.g. prestressed/post-tensioned beams, stressed-cable/tendon modeling) — with **no engine rewrite**. The **v1.1** jump is *vertical* (backend, accounts, cloud, IFC). The data model and abstractions in this spec are therefore generalized for breadth from day one (see §0.2).
**Region (v1.0):** France-Morocco. **Design basis:** dual selectable code packs — **BAEL 91 modifié 99** (default for Morocco) and **Eurocode 2 (EN 1992-1-1)** — plus **RPS 2000/2011** seismic overlay (Moroccan parasismic code). Region/code architecture is pluggable for later expansion.
**Deployment model:** Local-first, fully client-side, zero-cost hosting (static SPA). No backend in 1.0.

**Guiding principle:** RebarConfig is not a set of fixed templates — it is a **fully-parametric combination space**. Every axis (code · seismic regime · material · standard/convention · geometry · cross-section layout principle · bar shape · supplemental ties · cover/exposure · …) is an **independent, freely-combinable dimension**. The user has full control to find *any* combination that fits their case. The **only** constraint is **real construction logic** — the app allows everything buildable and blocks only what is physically or structurally invalid (see §0.1).

## 0. Executive Summary

RebarConfig is a browser-based **rebar detailing** tool (not a structural-analysis tool). The engineer supplies the required steel area (`As,req`) per zone — already obtained from analysis (ETABS/Robot/SAFE) or hand calc — and RebarConfig lets them lay out **real, construction-accurate, fully-parametric reinforcement**, see it in live 3D, get instant Eurocode-2 buildability/compliance feedback, and export the three deliverables that matter on site: **Bar Bending Schedule (BBS / nomenclature)**, **DXF detail sheets**, and a **printable PDF drawing sheet**.

The differentiator ("killer" feature) is the **parametric Reinforcement Scheme Library**: per element, a curated catalog of construction-valid reinforcement *schemes* (not just "longitudinal + stirrup"), each composed of fully-parametric **bar groups** plus a catalog of **supplemental reinforcement** add-ons (cross-ties, diagonal corner bars, bent-up bars, skin bars…). An **advanced builder** lets experts add/replace/remove bar groups freely.

## 0.1 Core Principle — The Parametric Combination Matrix [REF-SYS-050]

RebarConfig's design intent is **total parametric coverage**: the user can express any reinforcement configuration that a real detailer could draw on site. Rather than hard-wiring element→scheme combinations, the system treats detailing as the product of orthogonal **parameter axes**. A configuration is *any* point in this matrix; the app's job is to (a) let the user reach every valid point freely, and (b) refuse only the points that violate construction logic.

### Orthogonal axes (each independently selectable / parametric)
| Axis | Examples (v1.0, expandable) |
|---|---|
| **Region** | France-Morocco (more later) |
| **Concrete code** | BAEL 91-99 · Eurocode 2 |
| **Seismic regime** | None (gravity) · RPS 2000/2011 zone 1–4 + ductility class |
| **Material** | Concrete grade (fc28 / C-class), steel grade (FeE500 / B500B…), exposure class, **fire-resistance class** (R30…R120) |
| **Reinforcement technology** | Passive rebar (v1.0) · *(horizontal-scale targets:* pre-tensioned strand · post-tensioned tendon/cable *)* — an axis from day one so prestressing is a new value, not an engine change (see §0.2, [REF-EXT-GAP-6]) |
| **Standard / convention** | French *fiche de façonnage* (BBS, bend allowances) — pluggable |
| **Element type** | column · beam · pile · slab(×3) · stair (extensible) |
| **Geometry** | section dims, height/length/span, thickness, step geometry… |
| **Cross-section layout principle** | bars-per-face, layering, symmetry, bundling, equal-perimeter (circular), mesh (slab) |
| **Bar shape design** | every ShapeArchetype (droite, crochet, baïonnette, chapeau, relevé, cadre, étrier, épingle, diamant, hélice, treillis, diagonale…) |
| **Supplemental ties / add-ons** | cross-ties, diagonal corner bars, bent-up bars, skin bars, extra hoops, densified zones… |
| **Detailing params** | cover (incl. *cast-against-earth*), fire axis-distance, mandrel ø, hook type/angle, anchorage/lap/curtailment lengths, aggregate size |

> The user explicitly noted that **not every option is enumerated here** — the point is the *model*, not the list. Any new option is just a new value on an axis (a manifest entry / code-pack constant), never an engine change.

### Construction-Logic Validity Layer [REF-MATH-050]
Because the matrix is huge, a dedicated layer governs which combinations are **buildable**. It has three tiers:

1. **Hard-invalid (blocked):** combinations that cannot physically exist or are structurally illegal under the active code (e.g. < min bars, spacing < min, mandrel < code min, supplement referencing a non-existent bar, helix on a rectangular section). These cannot be created/exported → 🔴.
2. **Discouraged (allowed + warned):** buildable but outside good practice or near a code limit (e.g. lap slightly short, unusual bar mix) → 🟠, exportable with a "review" stamp.
3. **Free:** everything else → 🟢.

The validity layer is **data-driven per code pack + seismic overlay**, so "what's allowed" follows the user's chosen axes. "Data-driven" here means a **hybrid**: a code pack supplies both **constants/limit tables** (cover, ratios, spacings) *and* a registry of **named predicate/formula functions** (`code.lbd(…)`, topological checks like *helix-on-rectangular* or *supplement-references-missing-bar*). Numeric limits are pure data; structural/topological rules are named functions the pack registers — adding a rule is a manifest+function pair, never an engine change. In **Guided mode** the UI only offers reachable/valid options (compatibility-filtered pickers); in **Advanced (expert) mode** the user may reach any point, with tier-1 still blocking and tier-2 warning. This is how "full control + every valid combination" and "can't build nonsense" coexist.

> 🧩 **[REF-EXT-GAP-0] — Axis & region expansion.** New regions, codes, conventions, or option values are added by extending an axis (new code pack, new manifest value) and, if needed, new validity rules. The matrix and engine are unchanged.

## 0.2 Scaling Model — Horizontal (breadth) before Vertical (depth) [REF-SYS-060]

RebarConfig grows **horizontally** across v1.0.x point releases and **vertically** at v1.1. The two directions are deliberately decoupled so breadth never waits on backend work.

| Direction | Releases | What it adds | Engine impact |
|---|---|---|---|
| **Horizontal (breadth)** | **v1.0.1, 1.0.2, …** | New **element types** (shear wall, footings, waffle slab, retaining wall, L/spiral stair…) and new **design principles** — notably **prestressed / post-tensioned beams** and **stressed-cable / tendon modeling**, plus new conventions (BS 8666, ACI 315) and regions/code packs | **None** — new manifests + (only for novel geometry) a registered generator. This is the design intent of §0.1 and the `REF-EXT-GAP-*` seams. |
| **Vertical (depth)** | **v1.1** | Backend (FastAPI), accounts, multi-tenant cloud storage, custom-scheme authoring/sharing, server-side **IFC** export | New service; the pure-TS engine (§2.1) is reused unchanged or ported. |

### 0.2.1 Generalized reinforcement abstraction (so prestressing is a manifest, not a rewrite) [REF-DATA-060]
The persisted/solved unit is a **`ReinforcingElement`** supertype, of which the v1.0 `BarGroup` (passive rebar) is the only concrete `kind`. Horizontal scaling adds new `kind`s **without changing the solver, validation dispatch, viewport, or exporter contracts** — each `kind` plugs into the same pipeline (§6) via its registered generator and validation profile.

```
ReinforcingElement (supertype)
 ├── kind: REBAR_GROUP        ← v1.0 (this spec) = BarGroup (§5.1)
 ├── kind: TENDON             ← horizontal-scale target (v1.0.x): pre/post-tension
 │      adds: prestressForce (P0, losses), strand/duct spec, profile path
 │      (parabolic/harped drape), live/dead-end anchorage, jacking sequence,
 │      validationProfile: PRESTRESS_*  (transfer + service stress limits)
 └── kind: …                  ← future technologies
```

Every `ReinforcingElement` exposes the same minimal interface the pipeline depends on: a **centerline path generator** (→ `centerline3D` + `cutLength`/`length`), a **placement binding** (§5.4), a **validation profile key**, and a **BBS/quantity record**. A `TENDON` differs from a `BarGroup` in its *generator* (drape profile vs bent polyline), its *validation profile* (prestress transfer/service stresses, duct cover, anchorage-zone bursting — not rebar ratios), and its *BBS record* (cable schedule + jacking force), **not** in how the engine orchestrates it.

> 🧩 **[REF-EXT-GAP-6] — Reinforcement-technology expansion.** A new technology (pre-tension, post-tension, external cable, FRP) is added as a new `ReinforcingElement.kind` with: (a) a registered generator, (b) a `validationProfile` in the relevant code pack, (c) a BBS/quantity record mapper. No change to the solver pipeline, store, viewport, or `.rcfg` envelope. v1.0 ships **only** `REBAR_GROUP`; the supertype exists now purely so v1.0.x can add `TENDON` without a refactor.

### 2.1 Component layers
- **UI / Controls (React + TS):** component-driven; a single typed state store (Zustand or Redux Toolkit) holds the active `Element` document. Every control mutation triggers a synchronous engine re-solve and a Three.js redraw (no reload, no network).
- **3D Viewport (Three.js):** concrete as semi-transparent volume (`MeshStandardMaterial`, opacity 0.30); rebar as solid `TubeGeometry` along computed centerlines. Failing bars recolor to absolute RED. OrbitControls; section-cut plane toggle.
- **Core Engine (framework-agnostic TS):** deterministic, pure functions. Same code reused by UI, exporters, and tests. **No engine code depends on React or the DOM** — this is what makes it testable and reusable in the 1.1 server.
- **Code Pack:** the EC2-FR rule/shape/convention bundle, loaded as data. Selecting a different pack (future) swaps detailing constants, mandrel tables, anchorage formulas, shape conventions, and BBS layout.

### 2.2 Why no backend in 1.0
Free hosting, offline capability, zero per-user cost, no auth surface. The downside (no IFC, no cloud sync) is explicitly deferred. **Constraint:** the engine must therefore be performant enough to re-solve + redraw a typical element in **< 16 ms** for slider drags (target 60 fps); heavy operations (export) may take longer and run off the interaction path.

**Performance fallback (normative).** The <16 ms budget is a target, not an assumption. The required degradation path when an element is heavy (many bars / dense ties / mesh): during an active drag, **(1)** debounce the full re-solve, **(2)** render bar **centerlines** (cheap `LineSegments`) instead of rebuilding `TubeGeometry`, and **(3)** defer full validation; on drag-release, run the full solve + tube rebuild + validation once. Layout and validation always run (correctness is never skipped on commit); only the per-frame *visual* fidelity degrades. This keeps interactivity bounded regardless of element size.

## 4. Contextual `As,req` Input Schema [REF-DATA-300]

Inputs are **zone-targeted**, never a single global number. Each element manifest declares its `As_zones[]`; the UI renders one labeled input per zone with the correct unit and a tooltip describing the structural meaning.

Example (beam `E-BEM-01`):
- `As_top_left` (cm²) — peak negative moment over left support.
- `As_top_right` (cm²) — peak negative moment over right support.
- `As_span_bottom` (cm²) — mid-span positive (sagging) moment.
- `Asw_shear` (cm²/m) — transverse steel per linear metre.

Each zone has: `key`, `label_fr`, `label_en`, `unit` (`cm2` | `cm2/m`), `kind` (`longitudinal` | `transverse`), and the **bar group(s) that satisfy it** (resolved by the scheme).

> 🧩 **[REF-EXT-GAP-2] — Zone schema expansion.** Add zones such as `As_punch` (punching shear, flat slab), two-way-slab `As_corner_torsion`, or retaining-wall face zones (`As_face_earth`, `As_face_air`) by appending to the element manifest's `As_zones[]`.

## 5. Parametric Reinforcement Model — THE CORE [REF-SHAPE-500]

This section replaces and greatly expands `[REF-EXT-GAP-3]` from the seed spec. It is the heart of the product.

### 5.1 Conceptual hierarchy

```
Element
 └── Reinforcement (a chosen Scheme instance)
      ├── base ReinforcingElement[]        ← defined by the scheme
      └── supplemental ReinforcingElement[] ← user-added from scheme's supplemental_catalog

ReinforcingElement (supertype — see §0.2.1)
 └── kind: REBAR_GROUP   ← the only v1.0 kind = BarGroup (below); TENDON etc. are horizontal-scale

BarGroup  (kind = REBAR_GROUP)
 ├── role: PRIMARY_LONGITUDINAL | TRANSVERSE | SUPPLEMENTAL | SKIN | DOWEL | STARTER | DISTRIBUTION
 ├── shapeArchetypeId   → ShapeArchetype (parametric segment grammar, §5.2)
 ├── params {}          → values for the archetype's parameters
 ├── diameter (mm)      → from code pack's allowed set
 ├── distribution       → Distribution (see §5.1.1) — count OR (segmented) spacing along a path
 └── placement: PlacementRule  → references host geometry (see §5.4)
```

### 5.1.1 Distribution — count or **segmented** spacing along a path [REF-DATA-510]
A single `countOrSpacing` value cannot express the spacing that real detailing requires (densified stirrups at member ends, support-zone double stirrups, seismic critical zones). The `distribution` field therefore supports **piecewise spacing along the placement path**:

```jsonc
"distribution": {
  "mode": "FIXED_COUNT",                  // a cross-section group (e.g. longitudinal bars)
  "count": 6
}
// — or —
"distribution": {
  "mode": "SPACING_ALONG_PATH",
  "path": "placement.path",               // resolved by §5.4 (e.g. column height, beam length)
  "segments": [                            // ordered; each covers a fraction or length of the path
    { "region": "END_BOTTOM", "extent": "l_c",          "spacing": 100 },
    { "region": "MIDDLE",     "extent": "remainder",    "spacing": 200 },
    { "region": "END_TOP",    "extent": "l_c",          "spacing": 100 }
  ]
}
```

- A **single-segment** `segments` array (`extent: "all"`) is the common uniform case and the authoring shorthand; the engine normalizes a bare `spacing` to it.
- `extent` accepts a length expression (e.g. `l_c` from the seismic overlay or `0.25*L`), `remainder`, or `all`.
- Each segment emits its own repeated instances; **validation runs per segment** (a mid-span spacing can PASS while a critical-zone spacing FAILs), and **BBS marks per segment** (identical sub-bars still merge by shape+φ+length across segments, §9.1).
- Segment boundaries are derived (not hand-placed) when an overlay defines them — e.g. the RPS overlay (§7.10) injects `END_*` segments of length `l_c` and sets their spacing; the user's single spacing becomes the `MIDDLE` value.

### 5.2 Shape Archetype — parametric segment grammar [REF-SHAPE-510]

A bar shape is **data**, not code. Each `ShapeArchetype` is a JSON definition of an ordered list of **segments** connected by **bends**, plus **end hooks**. The geometry solver turns it into a 3D polyline centerline (for the Three.js tube + 3D length) and a 2D projection (for DXF + *fiche de façonnage*).

```jsonc
// shapes/baionnette.json  (crank / offset bar)
{
  "id": "BAIONNETTE",
  "label_fr": "Baïonnette (barre à décrochement)",
  "plane": "2D",                       // 2D (planar) or 3D (e.g. helix, wrapped tie)
  "params": [
    { "key": "a", "label": "Longueur basse", "type": "length", "min": 0 },
    { "key": "b", "label": "Décalage (offset)", "type": "length", "min": 0 },
    { "key": "c", "label": "Longueur haute", "type": "length", "min": 0 },
    { "key": "slope_deg", "label": "Angle du décrochement", "type": "angle", "default": 45 }
  ],
  "closed": false,
  "segments": [
    { "line": "a", "dir": "u+" },                       // low run along bar axis
    { "turn": "slope_deg", "hand": "left" },            // bend into the crank
    { "line": "b / sin(slope_deg)" },                   // crank: perp offset b at slope_deg
    { "turn": "slope_deg", "hand": "right" },           // bend back parallel to axis
    { "line": "c" }                                     // high run
  ],
  "endHooks": { "start": "none", "end": "none" },
  "mandrelRule": "code.mandrelMin(diameter)",   // resolved from code pack (EC2 §8.3 / BAEL)
  "totalLengthExpr": "a + b/sin(slope_deg) + c + hookAllowances",
  "bendDeductionRule": "code.bendDeduction"      // per-bend allowance from active pack
}
```

**Built-in archetypes shipped in v1.0 (EC2-FR pack):**

| Id | French name | Used by |
|---|---|---|
| `DROITE` | Barre droite | all |
| `CROCHET_L` | Barre à crochet (L) | beams, slabs, anchorages |
| `U_BAR` | Chaise / U | slabs, ties |
| `BAIONNETTE` | Baïonnette (crank) | columns (lap offset), beams |
| `CHAPEAU` | Chapeau (top bar over support) | beams, slabs |
| `RELEVE` | Acier relevé (bent-up) | beams (supplemental) |
| `CADRE_RECT` | Cadre rectangulaire (closed rect. tie) | columns, beams |
| `ETRIER` | Étrier (open/2-leg stirrup) | beams |
| `EPINGLE` | Épingle (single-leg cross-tie) | columns, beams (supplemental) |
| `CADRE_DIAMANT` | Cadre losange/diamant (interior tie) | columns (supplemental) |
| `SPIRALE_HELICE` | Spirale / hélice (3D helix) | circular columns, piles |
| `TREILLIS_MESH` | Treillis soudé / nappe (mesh mat) | slabs |
| `DIAGONALE_ANGLE` | Barre diagonale d'angle | columns/beams (supplemental) |
| `MARCHE_PALIER` | Barre principale escalier (waist + landing bend) | stairs |

Each archetype emits:
- **`centerline3D`** — ordered `[x,y,z]` points (bends approximated as poly-arcs at the mandrel radius for fidelity).
- **`cutLength`** — fabrication length per code pack (segment sum ± bend deductions + hook allowances).
- **`fiche`** — the *fiche de façonnage* representation: ordered segments with labeled lengths `a,b,c…`, bend angles, mandrel ø, sketch hints.

#### 5.2.1 Segment grammar — normative contract [REF-SHAPE-511]
The example above is illustrative; the following is the contract the **generic generator** implements. It removes every ambiguity flagged in review (turn direction, frame, closed loops, hook geometry, fillets, expression scope).

**(a) Local coordinate frame.** Each archetype is authored in its own right-handed frame `(u, v, w)`: `u` = primary run direction, `v` = in-plane lateral, `w` = out-of-plane normal. The **local origin is the start of the first segment, on the bar centerline.** For `plane:"2D"` archetypes all geometry lies in `u–v` (`w=0`). The 3D **orientation and position of this plane is supplied by the PlacementRule** (§5.4) as a rigid transform `T(origin, basis)`; the shape never hard-codes world orientation. This is why one `CADRE_RECT` archetype serves a column tie, a beam stirrup, and a pile hoop — only `T` differs.

**(b) Segment ops (turtle/LOGO model).** `segments[]` is an ordered op list evaluated as a heading-carrying pen in the local frame:
| Op | Fields | Effect |
|---|---|---|
| `line` | `len_expr`, optional `dir` (`u+ \| u- \| v+ \| v-` or absolute heading °) | advance `len_expr` along current (or given) heading; emits a straight residual |
| `turn` | `angle_expr`, `hand` (`left`\|`right`) | rotate heading by `angle`; **`hand` fixes the bend direction** (resolves the prior ambiguity). Marks a **bend vertex** (filleted, see (e)) |
| `arc`  | `angle_expr`, `radius_expr`, `hand` | sweep a circular arc (circular ties, spiral pitch turns) |
| `hook` | `hookRef` | emit an end/inline hook (see (d)) |

Headings are in the `u–v` plane for 2D archetypes; a 3D archetype (helix) is not expressed with this op list — it uses a bespoke generator (see (g)).

**(c) Closed shapes.** `"closed": true` welds the last emitted vertex to the first (all ties: `CADRE_RECT`, `CADRE_DIAMANT`, circular hoop). The generator verifies geometric closure within tolerance and treats the closing corner as a filleted bend. Hook legs on a closed shape overlap inward from the closing corner (e.g. the two 135° legs of a seismic `CADRE_RECT`).

**(d) Hooks.** `endHooks: { start, end }` and inline `{hook: <ref>}` resolve to a hook descriptor:
```jsonc
{ "angle": 90 | 135 | 180, "ext_expr": "max(10*diameter, 70)", "mandrel": "code.mandrelMin(diameter)" }
```
`angle`, minimum extension `ext_expr`, and `mandrel` come from the active code pack; the **seismic overlay (§7.10) can force `angle:135` and `ext ≥ 10φ`** on ties/cross-ties/épingles. `"none"` emits nothing.

**(e) Mandrel fillets & lengths.** Every `turn`/closed-corner vertex is replaced by a tangent circular arc of **centerline radius `r = mandrelDiameter/2 + diameter/2`**. `centerline3D` samples straights + fillet arcs at a fixed chord tolerance (for the Three.js tube and the 3D length). `cutLength` (fabrication length) = Σ straight residuals + Σ arc centerline lengths + Σ hook allowances **−** Σ `code.bendDeduction(angle, diameter)` so the cut length matches site practice, **not** the naive polyline sum. `fiche` reports the labelled segment dims `a,b,c…`, each bend angle, and the mandrel ø.

**(f) Expression scope (mathjs).** `len_expr`, `angle_expr`, `totalLengthExpr`, `ext_expr` evaluate against a **frozen, side-effect-free** scope: every archetype `param` by key, plus `diameter`, `mandrelDiameter`, `hookAllowances`, math helpers (`sin`,`cos`,`tan`,`min`,`max`,`sqrt`,…), and a read-only `code.*` namespace exposing pack functions (`code.mandrelMin(d)`, `code.bendDeduction(angle,d)`, `code.lbd(d,bond,fck,fyk)`, `code.l0(...)`). Evaluation is deterministic; unknown symbols are a manifest-load error (§11, S1).

**(g) Generator split (the only code seam for geometry).** The **generic segment-grammar generator** handles **every open or closed planar polyline bent bar with parameterized hooks** — all of: `DROITE, CROCHET_L, U_BAR, BAIONNETTE, CHAPEAU, RELEVE, CADRE_RECT, ETRIER, EPINGLE, CADRE_DIAMANT, DIAGONALE_ANGLE, MARCHE_PALIER, ATTENTE`. Exactly two v1.0 archetypes are **bespoke registered generators** because their centerline is not a planar polyline:
- `SPIRALE_HELICE` — parameterized 3D helix (`pitch`, `turns`/`height`, `helix_diameter`, end hooks).
- `TREILLIS_MESH` — orthogonal welded mat (`pitch_x`, `pitch_y`, `overhang_*`, panel extents).

A new non-polyline shape (multi-leg confinement hoop with internal cross-legs, Z-bar, trombone) is added by either expressing it in the grammar above or, if it cannot be, registering one generator in the shape registry (§6). Nothing else in the pipeline changes.

**(h) Worked closed example — `CADRE_RECT` (rectangular tie with 135° seismic hooks):**
```jsonc
{
  "id": "CADRE_RECT", "label_fr": "Cadre rectangulaire", "plane": "2D", "closed": true,
  "params": [
    { "key": "w", "label": "Largeur entre axes", "type": "length", "min": 0 },
    { "key": "h", "label": "Hauteur entre axes", "type": "length", "min": 0 }
  ],
  "segments": [
    { "line": "w", "dir": "u+" }, { "turn": 90, "hand": "left" },
    { "line": "h" },              { "turn": 90, "hand": "left" },
    { "line": "w" },              { "turn": 90, "hand": "left" },
    { "line": "h" }
  ],
  "endHooks": {
    "start": { "angle": 135, "ext_expr": "max(10*diameter, 70)", "mandrel": "code.mandrelMin(diameter)" },
    "end":   { "angle": 135, "ext_expr": "max(10*diameter, 70)", "mandrel": "code.mandrelMin(diameter)" }
  },
  "mandrelRule": "code.mandrelMin(diameter)",
  "totalLengthExpr": "2*(w+h) + 2*hookExt - bendDeductions"
}
```
Under a gravity code the two hooks default to `135°` already (good practice); the seismic overlay makes `135°`/`ext ≥ 10φ` mandatory and FAILs `90°`.

> 🧩 **[REF-EXT-GAP-3] — Bar archetype routing.** New shapes (e.g. multi-leg confinement hoops with seismic 135° hooks, Z-bars, trombones) are added as new `shapes/<id>.json` + an optional registered generator function if the segment grammar can't express them declaratively. The grammar covers all planar bent bars and parameterized helices natively.

### 5.4 Placement Rules & Host-Geometry References [REF-SHAPE-530]

`PlacementRule` is how a bar group is positioned **relative to the element and to other bars** — this is what makes supplements parametric and self-updating.

Reference targets a placement can bind to:
- **`corners[i]`** — corner index of the section (rect: 0–3; from the longitudinal layout).
- **`faces[edge]`** — `TOP|BOTTOM|LEFT|RIGHT` (rect) or angular position (circular).
- **`barIndices[i,j,…]`** — specific primary longitudinal bars (e.g. an *épingle* links bars `i` and `j`).
- **`zone`** — a named reinforcement zone (`As_top_left`, support region, mid-span…).
- **`path`** — a curve along which transverse bars repeat (column height, beam length, spiral axis).
- **`coordinate`** — explicit offset (advanced builder only).

Distribution modes: `FIXED_COUNT`, `SPACING_ALONG_PATH`, `EQUAL_PERIMETER`, `LAYERED` (multi-row with inter-layer clear gap), `SYMMETRIC`.

This reference system is what enables the **2D, multi-layer** column/beam cross-section layout (the seed spec's §5.2 1-D formula is generalized — see §7.2).

### 5.5 Supplemental Reinforcement [REF-SHAPE-540]

A **supplemental group** is a `BarGroup` with `role: SUPPLEMENTAL` (or `SKIN`/`DOWEL`) whose placement **references the resolved base layout**. The scheme's `supplementalCatalog` lists which are construction-valid for that scheme; the user adds them from a dedicated **"Armatures complémentaires"** panel, then parametrizes them.

  "id": "SUPP_EPINGLE_CROSSTIE",

  "shape": "EPINGLE",
  "requires": { "hostRole": "PRIMARY_LONGITUDINAL", "min_bars": 4 },
  "placement": {
    "rule": "LINK_BAR_PAIR",
    "select": "user",            // user clicks two longitudinal bars in 3D / picks indices
    "spacing": "= tie.spacing"   // follows the tie spacing along the height by default
  },
  "params": [
    { "key": "diameter", "type": "diameter", "default": 8 },
    { "key": "hook_angle", "type": "angle", "default": 135 }  // EC2 seismic hook option
  ],

```

Examples shipped v1.0:
- **`SUPP_EPINGLE_CROSSTIE`** — épingle linking an interior bar pair (column/beam).
- **`SUPP_DIAGONALE_ANGLE`** — diagonal/inclined bar at a section corner (your column example).
- **`SUPP_RELEVE_BARS`** — bent-up bars (aciers relevés) in beams.
- **`SUPP_SKIN_SIDE`** — armatures de peau on tall sections.
- **`SUPP_DIAMANT_TIE`** — interior diamond confinement tie.
- **`SUPP_DOUBLE_STIRRUP_SUPPORT`** — densified stirrups in support/joint zones.
- **`SUPP_HEAD_HOOPS`** — extra hoops at pile/column head.

**Behaviour:** when a base bar moves (param change), every supplement bound to it re-solves automatically. If a referenced bar is deleted, the supplement is flagged invalid (WARN) and the user is prompted to rebind or remove it. The 3D canvas lets the user **click base bars to define a supplement's references** (e.g. click two bars → create an épingle between them).

> 🧩 **[REF-EXT-GAP-5] — Supplemental archetype expansion.** New supplemental add-ons are added as `supplements/<id>.json` + listed in any scheme's `supplementalCatalog`. The `requires`/`placement.select` fields keep them construction-valid.

### 5.6 Authoring modes [REF-SHAPE-550]
- **Guided (default):** pick element → pick scheme → set geometry → set diameters/counts/spacings per zone → add supplements from the catalog. The validator prevents non-buildable states.
- **Advanced builder:** "Mode expert" toggle reveals the bar-group list; the user can add/replace/remove any group, choose any archetype, and place via explicit references/coordinates. Validation still runs but warnings (not hard locks) are permitted so experts aren't blocked. **Custom scheme *saving* is not in v1.0** (1.1 with accounts) — but an advanced layout persists fully inside the `.rcfg` project file.

## 6. Geometry Solver & Shape Registry [REF-SYS-600]

The solver is a pipeline (pure functions):

```
Element params + Reinforcement(scheme + groups)
   │
   ▼ 1. Layout solver  → positions of each bar in the cross-section / along paths
   │     (handles layers, covers, stirrup offset, equal spacing, symmetry)
   ▼ 2. Shape generator → for each bar group, build centerline3D + cutLength + fiche
   │     (looks up ShapeArchetype; resolves params, mandrel, hooks via code pack)
   ▼ 3. Assembly        → full 3D bar set (instanced), concrete envelope mesh
   ▼ 4. Validation      → run code rule-set → per-group + element status
   ▼ 5. Outputs         → viewport meshes, BBS records, DXF projections, PDF model
```

**Shape registry:** a map `archetypeId → generator`. Most archetypes are handled by the **generic segment-grammar generator**; only genuinely special ones (helix, mesh) register a bespoke generator. This is the single extension seam for novel geometry.

### 6.1 Layout solver — cross-section bar placement (normative) [REF-SYS-610]
Step 1 of the pipeline turns a **layout descriptor** into bar **centroid positions**. The descriptor is either explicit per-face counts or a total + principle. The seed spec's 1-D spacing formula is generalized here to the 2-D, multi-layer, corner-sharing case.

**Common quantities.** Cover-to-bar-centroid inset from each face: `d' = c + φ_t + φ_ℓ/2` (`c` nominal cover, `φ_t` stirrup/tie ø, `φ_ℓ` longitudinal ø). The **core rectangle** has corners at the four section corners inset by `d'`.

**Effective depth `d` — computed, not assumed [REF-SYS-611].** Because the solver resolves the *real* bar positions, `d` is computed exactly per flexural zone rather than approximated as `0.9h`. For a zone whose tension face is `F`, `d = D_F − ȳ_t`, where `D_F` is the section depth measured from the compression fibre opposite `F` and `ȳ_t` is the **area-weighted centroid** of that zone's tension bars summed across layers: `ȳ_t = Σ(A_i·y_i)/ΣA_i`. The compression/tension faces follow the zone — sagging/span → bottom bars in tension, `d` from the top fibre; hogging/`CHAPEAU` over a support → top bars in tension, `d` from the bottom fibre. The solver emits `d` (and `d'`) per zone, and **every rule that uses `d` consumes this computed value** (§7.4 `As,min`, §7.5 shear spacing, §7.7 anchorage lever arm). This is a deliberate accuracy gain over rule-of-thumb detailing and is surfaced in the UI (§8).

**Rectangular section (`E-COL-01`, `E-BEM-01`):**
1. **Place the 4 corner bars first**, at the core-rectangle corners. Corner bars are **shared between the two faces they touch and counted once** (avoids the classic double-count). The descriptor's per-face counts `nTop, nBottom, nLeft, nRight` are **inclusive of their two corner bars**.
2. **Intermediate bars per face** = `nFace − 2`, distributed at **equal centre-to-centre spacing along the core edge** between that face's two corner bars. `nFace < 2` on any occupied face → **tier-1 hard-invalid** (§0.1).
3. **Total provided bars** `N = 4 + Σ_face (nFace − 2)` over the four faces; this `N` feeds §7.1 `As,provided`. Beams typically occupy only `TOP`/`BOTTOM` (set `nLeft=nRight=2`, i.e. corners only) unless skin bars (`SUPP_SKIN_SIDE`) populate the sides.
4. **`LAYERED`**: extra rows are inset from the face by `φ_ℓ + g` where `g = max(s_clear,min, user inter-layer gap)`; each inner layer re-runs steps 1–3 on its shrunken core. Layer count and per-layer counts come from the descriptor.
5. **`SYMMETRIC`**: enforce `nLeft=nRight` and `nTop=nBottom` with mirrored intermediate positions (default for columns).
6. **Clear-spacing check** (§7.2) runs **per face and per layer** on the resulting positions; vertical clear gap between layers is checked identically.

**Circular section (`E-COL-02`, `E-FND-01`) — `EQUAL_PERIMETER`:** `N` longitudinal bars on the **pitch circle** of radius `R_p = D/2 − c − φ_t − φ_ℓ/2`, at angular step `360°/N` from a datum. Clear spacing is checked along the pitch-circle arc: `s_arc = 2·R_p·sin(180°/N) − φ_ℓ`. Min bars **6** (§7.4).

**Slabs/mats:** placement is a 1-D bar line per direction at `pitch = spacing`, offset by cover; the mat itself is the `TREILLIS_MESH` generator. Spacing limits per §7.4 (`s_max`).

The layout solver output is a list of `{ position(u,v in section frame), faceTag, layerIndex, isCorner }` consumed by step 2 (shape generation) and by placement bindings that reference `corners[i]` / `faces[edge]` / `barIndices[…]` (§5.4).

## 7. Validation & Code-Compliance Engine [REF-MATH-700]

Replaces seed §5. Validation runs on every state change (target < 16 ms). Each rule returns `{status: PASS|WARN|FAIL, value, limit, codeRef, message_fr, message_en, affectedGroupIds[]}`.

**Code-pack driven.** The rules below are stated with Eurocode-2 references for concreteness, but every constant and formula is supplied by the **active code pack**. v1.0 ships two packs whose values differ:
- **BAEL 91-99** (default, Morocco): cover/enrobage, `l_s` scellement/anchorage (`l_s = φ·f_e/(4·τ_su)`), lap lengths, `A_min`/`A_max` per BAEL/CBA 93, min bar counts, tie spacing rules, French bar grades (FeE500 → `f_e`, concrete `f_c28`).
- **Eurocode 2 (EN 1992-1-1)**: the §7.1–7.8 formulas as written (`l_bd`, `l_0`, ρ-limits, `s_cl,tmax`, mandrel 4φ/7φ, cover `c_min+Δc_dev`).

Each rule carries a `codeRef` so alerts cite the exact clause of whichever pack is active. The **construction-logic validity layer (§0.1 / [REF-MATH-050])** sits above these rules and assigns the hard-block / warn / free tier.

### 7.1 Provided area (per zone)
$$A_{s,\text{provided}}^{(z)} = \sum_{i \in \text{group}(z)} n_i \cdot \frac{\pi \phi_i^2}{4}$$
summed over the bar groups assigned to zone `z`. **FAIL** if `< As_req(z)`.

### 7.2 Clear spacing — generalized (multi-layer, 2D)
The seed §5.2 1-D formula is generalized. For a layer of `N` equal bars on a face of clear width `W`:
$$s_{\text{clear}} = \frac{W - 2c - 2\phi_{t} - N\phi_{\ell}}{N - 1}$$
where `c` = nominal cover, `φ_t` = transverse (stirrup) diameter, `φ_ℓ` = longitudinal diameter. For multiple layers, the **vertical clear gap** between layers is checked the same way. For circular/spiral, spacing is checked along the pitch circle perimeter. **EC2 §8.2 minimum:**
$$s_{\text{clear,min}} = \max(\phi_\ell,\; d_g + 5\text{ mm},\; 20\text{ mm})$$
where `d_g` = max aggregate size (user input, default 20 mm). **FAIL** if `s_clear < s_clear,min`.

### 7.3 Cover (EC2 §4.4 + fire EN 1992-1-2)
`c_nom = c_min + Δc_dev` (Δc_dev default 10 mm). `c_min ≥ max(φ, c_min,dur(exposure class), c_min,fire, 10 mm)`. Exposure class is a user input (XC1…XS3), plus a dedicated **`CAST_AGAINST_EARTH`** condition (`c_nom ≥ 65–75 mm`) used by the drilled-shaft pile and future footings. **Fire resistance** is an optional user input (R30/R60/R90/R120 → minimum **axis distance** `a` per the EN 1992-1-2 tabulated method, or its BAEL/DTU equivalent); the implied `c_min,fire = a − φ_t − φ_ℓ/2` is folded into the check because **fire frequently governs** beams/columns/slabs. **FAIL** if user cover < `c_nom` (durability **or** fire).

### 7.4 Reinforcement ratio limits
- **Columns (EC2 §9.5):** `As,min = max(0.10·N_Ed/f_yd, 0.002·A_c)` — *N_Ed optional; if absent, use 0.002·Ac*; `As,max = 0.04·A_c` (0.08 at laps). Min bars: **4** (rect), **6** (circular). **FAIL** outside range.
- **Beams (EC2 §9.2):** `As,min = max(0.26·(f_ctm/f_yk)·b·d, 0.0013·b·d)`; `As,max = 0.04·A_c`.
- **Slabs (EC2 §9.3):** `As,min` as beams; **max bar spacing** `s_max` ≤ min(3h, 400 mm) (principal), ≤ min(3.5h, 450 mm) (secondary). **Secondary/distribution steel** `As_dist ≥ 0.20·As_main` (EC2 §9.3.1.1(2)) → **FAIL** below. For two-way slabs with **restrained discontinuous corners**, `As_corner_torsion` (top + bottom mats, ≈ ¾ of the larger mid-span steel over ⅕ of the short span) is required when the corner is held down → **WARN** if flagged restrained and the zone is empty.

### 7.5 Transverse / confinement (EC2 §9.5.3 columns, §9.2.2 beams)
- Column tie spacing `s_cl,tmax = min(20·φ_ℓ, b_min, 400 mm)`; ×0.6 in joint/lap zones.
- Tie diameter ≥ max(6 mm, φ_ℓ/4); the tie mandrel must also **clear the enclosed longitudinal bar** (`mandrel ≥ φ_ℓ`).
- Beam max stirrup spacing `s_l,max = 0.75·d` (uses the **computed `d`**, §6.1).
- **EC2 minimum shear ratio:** `ρ_w = Asw/(s·b_w·sinα) ≥ ρ_w,min = 0.08·√f_ck / f_yk` → **FAIL** below (the BAEL pack's equivalent is the `0.4 MPa` rule in §7.11).

**Leg-counted provided transverse area (normative).** `Asw` per metre is computed from the number of legs crossing the shear/confinement plane, **not** from a single closed tie: `Asw,provided/m = (n_legs · (π·φ_t²/4) · 1000) / s`, where `n_legs` is derived from the resolved geometry — a `CADRE_RECT` contributes 2 legs, and every bound cross-tie / `EPINGLE` / `CADRE_DIAMANT` that crosses the plane adds its legs. This makes a 4-leg arrangement correctly provide ~2× the 2-leg `Asw/s` at the same spacing. Compare `Asw,provided/m` vs `Asw,req` per zone; **WARN/FAIL** accordingly.

**Distribution start offset.** Stirrup/tie sets begin at **`s/2` from the support/member face** (BAEL practice; EC2 ≤ `0.5·s` from the face), so the `SPACING_ALONG_PATH` generator (§5.1.1) applies a leading half-space offset rather than emitting the first link exactly at the path origin.

### 7.6 Mandrel diameter / bend feasibility (EC2 §8.3)
Baseline min mandrel ø: **4φ** (φ ≤ 16 mm), **7φ** (φ > 16 mm). **Bearing-stress-in-bend check (EC2 §8.3(3)):** where the bar is highly stressed and the cover perpendicular to the bend plane or the bar spacing is small, the governing mandrel can exceed `7φ` to prevent concrete crushing inside the bend: `φ_m,min ≥ F_bt·((1/a_b) + 1/(2φ)) / f_cd`, with `a_b` = half the centre-to-centre bar spacing (or `cover + φ/2` for an edge bar). The solver knows cover and spacing, so it takes `φ_m = max(baseline, bearing-stress value)`. The fiche/cutLength uses the governing mandrel; if a user-set bend radius is smaller → **FAIL** (concrete crushing / cracking risk).

### 7.7 Anchorage, lap & curtailment (EC2 §8.4, §8.7, §9.2.1.3–.5)
`l_bd` (design anchorage) and `l_0` (lap) are computed from `l_b,rqd = (φ/4)·(σ_sd/f_bd)` with `f_bd = 2.25·η₁·η₂·f_ctd`, then `l_bd = α₁α₂α₃α₄α₅·l_b,rqd ≥ l_b,min` and `l_0 = α₆·l_bd`. Material defaults: C25/30, B500B. Three things the engine computes **because it knows the geometry** (instead of asking the user):

1. **`As,req/As,prov` stress reduction.** `σ_sd = f_yd·(As,req/As,prov)` per zone (both quantities are known, §7.1), so anchorage/lap shorten legitimately exactly as a detailer would — clamped to `l_b,min`.
2. **Automatic bond-condition classification.** `η₁` (1.0 good / 0.7 poor, EC2 Fig 8.2) is set from each bar's resolved position relative to the casting direction — top bars with > 250 mm of fresh concrete below them are auto-classified poor-bond. No manual bond toggle.
3. **`α` coefficients** for bar shape, cover, and confinement by transverse reinforcement are taken from the resolved cover/tie layout; `α₆` (lap) from the **% of bars lapped at the section** (1.0–1.5). Coefficients not yet modeled default to 1.0 and are disclosed in the alert.

Hooks/baïonnette segment lengths must satisfy `l_bd`; lap zones must satisfy `l_0`. **End-support bottom-bar anchorage (EC2 §9.2.1.4):** at least `β·As,span` (β = 0.25) of bottom steel is carried past the support face and anchored for the shifted tensile force → **WARN** if absent/short (predicate `end_support_anchorage_short`, §7.13).

**Curtailment & the shift rule (EC2 §9.2.1.3).** Longitudinal bars that stop short of the member end — span bottom bars near supports and `CHAPEAU` top bars over supports — carry a parametrized extension `a_l + l_bd` beyond their theoretical cut-off, where the **shift** `a_l ≈ z·cotθ/2` (default `≈ d` for members with shear links). The chapeau extension into the span defaults to `l_support_zone + a_l + l_bd`. These code-derived lengths flow into each bar's `cutLength` and the BBS, so **support/curtailed bar lengths are correct on site rather than user-guessed**. A tier-1 anchorage/lap below the required `l_bd`/`l_0` is **FAIL** (§7.12); within the tolerance band above it, **WARN**.

### 7.8 Aggregate vs spacing
`s_clear ≥ d_g + 5 mm` (folded into §7.2).

### 7.9 Deterministic UI status (seed §5.3, refined)
- **🟢 PASS** — all rules PASS. All export triggers enabled.
- **🟠 WARN** — no FAIL, but ≥1 WARN (e.g. lap slightly short, spacing near limit). Exports **enabled** but PDF/BBS stamped "À vérifier / Review required" and the alert panel lists warnings.
- **🔴 FAIL** — ≥1 FAIL (insufficient steel, spacing < min, ratio out of range, bend infeasible). Failing bars render **RED** in 3D; **export compilation is locked**; alert panel explains each failure with the value and the EC2 limit.

### 7.10 Seismic overlay — RPS 2000/2011 [REF-MATH-710]
A **seismic overlay** activates when the user sets a seismic regime (RPS zone + ductility class ND1/ND2/ND3). It is applied *on top of* the chosen concrete code (BAEL or EC2) and is a separate composable data module (`codepacks/seismic/RPS-2011.json`). When seismic = None the overlay is inert (pure gravity detailing).

**Overlay mechanism (how it composes).** The overlay does not replace the base pack; it (1) **injects critical-zone segments** into transverse `distribution` (§5.1.1), (2) **tightens limits** (overrides specific constants the base pack supplies), (3) **forces hook geometry** (135°/10φ on ties/cross-ties/épingles, §5.2.1d), and (4) **promotes optional confinement supplements to required**. Each effect is a declared override keyed to a base-rule id, so the same overlay rides on either BAEL or EC2.

**(a) Critical (plastic-hinge) zone length `l_c`.** Auto-derived at member ends/joints and shaded in 3D. Indicative relations (⚠ **VERIFY against RPS 2011 text before M4** — these are pre-filled defaults, not adopted values):
- Columns: `l_c = max(h_section_max, H_clear/6, 450 mm)`.
- Beams: `l_c = 2·h` from each support face.
The overlay writes `END_*` segments of length `l_c` into the member's transverse distribution (§5.1.1); the user's spacing becomes the `MIDDLE` segment value.

**(b) Confinement spacing in critical zones (densification).** Per ductility class; **FAIL** if user spacing in an `END_*` segment exceeds the limit:

| Parameter | ND1 | ND2 | ND3 | Source |
|---|---|---|---|---|
| Critical-zone tie spacing `s_crit ≤` | `min(12φ_ℓ, 0.5·b_min, 200)` | `min(8φ_ℓ, 0.5·b_min, 150)` | `min(6φ_ℓ, 0.25·b_min, 100)` | ⚠ VERIFY (mm) |
| Min tie ø | `6 mm` | `8 mm` | `8 mm` | ⚠ VERIFY |
| Hook angle / extension | `135° / ≥10φ` | `135° / ≥10φ` | `135° / ≥10φ` | RPS (firm) |
| Required confinement add-ons | cross-ties as needed | cross-ties + diamond | cross-ties + diamond, every long. bar engaged | ⚠ VERIFY |
| Min longitudinal ratio uplift | base | tightened | further tightened | ⚠ VERIFY |

> The numeric cells marked ⚠ are **structured placeholders with engineer-supplied defaults**, isolated in `RPS-2011.json` so a structural engineer fills/ratifies them without touching the engine. The **table shape, the override mechanism, and the dispatch are final**; only the cell values await sign-off (§14.5). This is the honest state: the overlay is fully specified *structurally*, pending code-text ratification of constants.

**(c) Other overlay effects.**
- **135° seismic hooks** mandatory on ties/cross-ties/épingles (`ext ≥ 10φ`); the supplemental engine defaults to 135° under RPS and **FAIL**s 90° hooks in seismic members.
- **Confinement add-ons** (cross-ties/diamond ties) become **required** for the section's bar arrangement; the supplemental panel pre-loads them and the validity layer (§0.1) blocks export until present.
- **Min longitudinal ratio** and **max tie spacing** tightened per the table; these override the base pack's §7.4/§7.5 constants only while the overlay is active.
- **Laps & splices forbidden in critical zones (ND2/ND3).** A lap (`l_0`) or starter/baïonnette splice whose extent intersects an `END_*`/`l_c` segment is **tier-1 FAIL** under ND2/ND3 (relaxed to WARN for ND1) — the engine already knows both the lap extent and `l_c`, so it blocks splices placed in the plastic-hinge region and steers column splices to mid-height (predicate `lap_in_critical_zone`, §7.13).

**Zone count note.** §0.1/§8 reference "zone 1–4"; RPS 2000 vs RPS 2011 differ in zonation (acceleration vs velocity zoning). The zone enum and its `a_g` mapping live in `RPS-2011.json` and are a §14.5 sign-off item — the engine treats zone purely as a key into that table.

### 7.11 BAEL 91 mod. 99 pack — constants & formulas (the default path) [REF-MATH-720]
§7.1–7.8 above are written in EC2 terms; because **BAEL is the v1.0 default**, its rule set is enumerated here to the same level, so the default user path is fully specified. All values carry `codeRef` (`BAEL 91-99` / `CBA 93`). ⚠ The formulas are the standard BAEL relations; **the assembled constants table is a §14.5 engineer sign-off item** (isolated in `codepacks/BAEL-FR/`), but the engine needs none of them hard-coded.

| Quantity | BAEL formula / limit | Notes |
|---|---|---|
| Tensile strength | `f_t28 = 0.6 + 0.06·f_c28` (MPa, f_c28 ≤ 60) | C25 → `f_t28 = 2.1` |
| Steel design stress | `f_su = f_e / γ_s`, `γ_s = 1.15` | FeE500 → `435 MPa` |
| Bond stress (HA) | `τ_su = 0.6·ψ_s²·f_t28`, `ψ_s = 1.5` → `1.35·f_t28` | C25 → `≈ 2.84 MPa` |
| Straight anchorage (scellement) | `l_s = φ·f_e / (4·τ_su)` | FeE500/C25 → `≈ 40φ` (tabulated) |
| Hooked anchorage | `l_a ≈ 0.4·l_s` (crochet normal) | replaces straight where hooked |
| Lap (recouvrement, tension) | `l_r = l_s` (×1.5 if >½ bars spliced at a section) | maps to §7.7 `l_0` role |
| Beam `A_s,min` (non-fragilité) | `A_min = 0.23·b·d·(f_t28/f_e)` | replaces EC2 §9.2 min |
| Beam/col `A_s,max` | `A_max = 5%·B` (B = gross concrete area) | EC2 used 0.04·A_c |
| Column `A_s,min` | `max(4 cm²/m of perimeter, 0.2%·B)` | min bars **4** rect / **6** circular |
| Long-bar transverse spacing (col) | `≤ min(a + 10 cm, 40 cm)` (`a` = smaller side) | layout constraint |
| Column tie spacing (zone courante) | `s_t ≤ min(15·φ_ℓ,min, 40 cm, a + 10 cm)` | tie ø `φ_t ≥ φ_ℓ,max / 3` |
| Beam stirrup spacing | `s_t ≤ min(0.9·d, 40 cm)`; first at `s_t/2` from support | min shear steel `A_t·f_e/(b_0·s_t) ≥ 0.4 MPa` |
| Slab bar spacing | principal `≤ min(3h, 33 cm)`; secondary `≤ min(4h, 45 cm)` | replaces EC2 §9.3 `s_max` |
| Cover (enrobage) | `5 cm` (mer/agressif) · `3 cm` (extérieur/condensation) · `1–2 cm` (intérieur protégé) · **`6.5–7.5 cm` (coffrage contre terre / cast against earth)** | default `3 cm`; **fire axis-distance may govern**; replaces EC2 §4.4 |
| Mandrel (rayon de cintrage) | per BAEL bend table by φ and bar role | feeds §5.2.1e / §7.6 |

These are exposed through the **same `code.*` function names** the EC2 pack implements (`code.lbd`, `code.l0`, `code.AsMin`, `code.tieSpacingMax`, `code.cover`, `code.mandrelMin`, `code.bendDeduction`), so archetypes, schemes, and the validator are **pack-agnostic** — selecting BAEL vs EC2 swaps the implementations behind those names, nothing else.

### 7.12 Severity policy — WARN vs FAIL (normative) [REF-MATH-730]
The tier assignment (§0.1) is made explicit so it is consistent and code-pack-portable. A rule is **FAIL (tier-1, blocks export)** when the state is physically impossible or structurally unsafe and unambiguous: insufficient `As` vs `As,req`; clear spacing `< s_clear,min`; ratio outside `[A_min, A_max]`; mandrel below code min; **anchorage/lap below the required `l_bd`/`l_0`** (corrected from r1, where these were WARN — short anchorage is an unsafe state, not a stylistic one); seismic critical-zone spacing exceeded; 90° hook in a seismic member; required confinement absent. A rule is **WARN (tier-2, exports with "À vérifier" stamp)** when the state is buildable but near a limit or outside good practice: spacing/lap within a configurable tolerance band *above* the minimum, unusual bar mixes, cover above durability min but below a comfort target, `N_Ed`-dependent column min computed without a supplied `N_Ed`. The tolerance band per rule lives in the code pack.

### 7.13 Topological / detailing-logic validity predicates [REF-MATH-740]
Beyond numeric limits, the validity layer (§0.1) registers **named topological predicates** — structural-detailing rules that depend on bar *arrangement*, not just a constant. Each is a pack/overlay-registered function returning the standard rule result and tier:

| Predicate | Tier | Rule |
|---|---|---|
| `helix_on_rectangular` / `supplement_refs_missing_bar` | 🔴 | physically impossible topology (retained from §0.1) |
| `lap_in_critical_zone` | 🔴 (ND2/3) · 🟠 (ND1) | lap/splice extent ∩ `l_c` ≠ ∅ in a seismic member (§7.10) |
| `stair_reentrant_corner_pullout` | 🔴 / 🟠 | a **tension** bar bent around a **re-entrant (concave) corner** (the flight↔landing kink in `MARCHE_PALIER`) — the bar must be split and separately anchored, never wrapped around the corner, or it spalls the cover. Detected from the bend concavity + the tension face |
| `slab_distribution_min` | 🔴 | `As_dist < 0.20·As_main` (§7.4) |
| `twoway_corner_torsion_missing` | 🟠 | restrained discontinuous corner with empty `As_corner_torsion` (§7.4) |
| `end_support_anchorage_short` | 🟠 | bottom steel not anchored past the end support (§7.7) |
| `crosstie_engagement` | 🟠 / 🔴 | seismic confinement requires alternate (ND2) / every (ND3) longitudinal bar laterally engaged by a tie corner or cross-tie (§7.10b) |

Adding a predicate is a manifest + function pair (§0.1), never an engine change. `stair_reentrant_corner_pullout` in particular encodes a classic detailing error that distinguishes a construction-aware tool from generic CAD geometry.

> 🧩 **[REF-MATH-700 / code-pack hook]** All limits/formulas above live in the active **code pack** (BAEL-FR / EC2) plus the optional **seismic overlay** (RPS-2011) as data + named functions. A future pack (ACI 318 + ASCE 7, BS 8666, other regions/seismic codes) supplies its own constants/formulas and overlay without touching the engine. This is the seed's `[REF-EXT-GAP-4]` realized as a pluggable layer, aligned with the combination-matrix axes (§0.1).

## 9. Export Engines [REF-SYS-900]

All client-side in v1.0.

### 9.1 BBS — Nomenclature d'armatures
Builds from each bar group's `cutLength`, count, diameter; weight = `length × count × unitMass(φ)`, with `unitMass(φ) = 0.006165·φ²` kg/m (i.e. `ρ_steel = 7850 kg/m³`, φ in mm) so the table is reproducible. Output: on-screen table + PDF, French *fiche de façonnage* style (shape sketch + a/b/c dims + mandrel). The BBS also reports a **steel-quantity summary**: total weight per diameter and the **steel ratio `kg/m³` of concrete** for the element (a standard sanity-check metric, from the gross concrete volume). An optional **stock-length cut optimization** nests cut lengths against a configurable stock bar length (default 12 m) and reports offcut waste % — a pure client-side post-process over the bar records. JSON form (per seed §7.2) is the canonical record:

```jsonc
{
  "element_summary": { "element_id": "B12", "total_weight_kg": 89.15 },
  "bar_records": [
    { "mark": "01", "shape": "DROITE",     "diameter_mm": 16, "length_mm": 5450, "quantity": 4,  "weight_kg": 34.42, "fiche": {…} },
    { "mark": "02", "shape": "CADRE_RECT", "diameter_mm": 8,  "length_mm": 1640, "quantity": 28, "weight_kg": 18.11, "fiche": {…} }
  ]
}
```
Marks are auto-assigned and stable; identical bars (same shape+dims+φ) merge to one mark with summed quantity.

### 9.2 DXF detail sheets
Project the 3D centerlines onto 2D planes (longitudinal elevation + cross-sections). Generated client-side (`@tarikjabiri/dxf` or equivalent). Strict layers:
- `COFFRAGE` — concrete formwork outline (grey, continuous).
- `ARMATURES` — bold rebar lines.
- `COTATION` — dimensions.
- `TEXTE` — annotations.
- **Label collision avoidance:** each annotation (e.g. `4 Φ 16 L=5450 e=15cm`) has a 2D bounding box; a tracker offsets overlapping labels with leader lines.

**Scope discipline (this is a sub-project, staged).** Clean 2D detailing from 3D projection is the largest single piece of M5. It is staged to de-risk: **(DXF-1, required v1.0)** longitudinal elevation + one representative cross-section per element, with fixed/templated dimension placement and the four strict layers; **(DXF-2, stretch within M5)** multiple cross-sections and the bounding-box leader-line collision solver above. Shipping DXF-1 fully is the v1.0 acceptance bar; DXF-2 may slip to 1.0.1 without blocking release. The `fiche` 2D projection (§5.2) is reused as the source geometry so projection logic is written once.

### 9.3 PDF drawing sheet
Title-blocked sheet (cartouche) bundling DXF views (as vectors) + the BBS table + project metadata + the global status stamp (🟢/🟠). Generated with `pdf-lib`/`jspdf`. Failing (🔴) state cannot export.

### 9.4 IFC — deferred to 1.1
`IfcReinforcingBar`/`IfcReinforcingMesh` (IFC4) via a server-side FastAPI + IfcOpenShell service, enabled only when cloud/accounts ship.

> 🧩 **[REF-EXT-GAP-4] — Regional detailing standards.** Bend formulas, shape-code books (BS 8666 numeric codes, ACI 315), and BBS layouts live in the code pack's `convention` module. The French *fiche* is the v1.0 convention; 1.0.1 adds others as data + a convention selector.

## 10. Project File Format `.rcfg` [REF-DATA-1000]

A single JSON document = the entire element state. Save → download file; "resume later" → import. Mirrored in IndexedDB for autosave/recovery.

```jsonc
{
  "rcfg_version": "1.0",
  "region": "FR-MA",
  "codePack": "BAEL-FR",                 // or "EC2"
  "seismic": { "code": "RPS-2011", "zone": 2, "ductility": "ND2" },  // or null (gravity)
  "units": { "length": "mm", "area": "cm2" },
  "element": {
    "type": "E-COL-01",
    "geometry": { "b": 300, "h": 600, "H": 3000 },
    "material": { "f_c28": 25, "f_e": 500, "exposure": "XC1", "d_g": 20 },
    "cover_mm": 30,
    "As_req": { "As_total": 12.0, "Asw_confinement": 4.5 }
  },
  "reinforcement": {
    "schemeId": "COL_TIES_CROSSTIE",
    "mode": "guided",
    "baseGroups": [
      {
        "id": "g-long",                       // stable id (referenced by supplements & marks)
        "kind": "REBAR_GROUP",                // ReinforcingElement discriminant (§0.2.1)
        "role": "PRIMARY_LONGITUDINAL",
        "zone": "As_total",                   // which As_zone this group satisfies
        "shapeArchetypeId": "DROITE",
        "params": {},                          // archetype param values (keys per shape manifest)
        "diameter": 16,
        "distribution": {                      // §5.1.1 — here a cross-section count
          "mode": "FIXED_COUNT", "count": 8
        },
        "placement": {                         // §5.4 — resolved/serialized binding
          "rule": "SECTION_PERIMETER",
          "layout": { "principle": "SYMMETRIC", "nTop": 3, "nBottom": 3, "nLeft": 2, "nRight": 2, "layers": 1 }
        }
      },
      {
        "id": "g-ties",
        "kind": "REBAR_GROUP",
        "role": "TRANSVERSE",
        "zone": "Asw_confinement",
        "shapeArchetypeId": "CADRE_RECT",
        "params": { "w": 240, "h": 540 },      // core-rect inner dims (derived/overridable)
        "diameter": 8,
        "distribution": {                      // §5.1.1 — segmented spacing along the height
          "mode": "SPACING_ALONG_PATH",
          "path": "placement.path",
          "segments": [                         // END_* injected by RPS overlay when seismic≠null
            { "region": "END_BOTTOM", "extent": "l_c", "spacing": 100 },
            { "region": "MIDDLE",     "extent": "remainder", "spacing": 200 },
            { "region": "END_TOP",    "extent": "l_c", "spacing": 100 }
          ]
        },
        "placement": { "rule": "ALONG_PATH", "path": { "ref": "COLUMN_HEIGHT" } }
      }
    ],
    "supplementalGroups": [
      {
        "id": "s-epingle-1",
        "kind": "REBAR_GROUP",
        "role": "SUPPLEMENTAL",
        "supplementId": "SUPP_EPINGLE_CROSSTIE",   // catalog entry it instantiates
        "shapeArchetypeId": "EPINGLE",
        "params": { "diameter": 8, "hook_angle": 135 },
        "diameter": 8,
        "distribution": { "mode": "SPACING_ALONG_PATH", "path": "= tie.spacing" },
        "placement": {                              // references resolved base bars by id
          "rule": "LINK_BAR_PAIR",
          "boundTo": { "group": "g-long", "barIndices": [1, 4] }   // re-solves if g-long changes
        }
      }
    ]
  },
  "meta": { "project": "…", "engineer": "…", "created": "…", "appBuild": "…" }
}
```

**Serialized `ReinforcingElement` contract (the engine I/O + persistence unit).** Every entry in `baseGroups`/`supplementalGroups` is a `ReinforcingElement` discriminated by `kind`. For `kind:"REBAR_GROUP"` (the only v1.0 kind) the required fields are exactly: `id`, `kind`, `role`, `zone` (or `supplementId` for supplements), `shapeArchetypeId`, `params`, `diameter`, `distribution` (§5.1.1), `placement` (§5.4). Placement bindings reference **stable ids** (`group`+`barIndices`, `corners[i]`, `faces[edge]`), so a base-bar change re-solves dependents and a deleted reference flags the supplement WARN (§5.5).

**Horizontal-scale forward-compat.** A future `kind:"TENDON"` (§0.2.1) serializes in the same array with its own fields (`profile`, `prestressForce`, `anchorage`, `validationProfile`) and `distribution` describing strand/duct layout. The `.rcfg` envelope, the `reinforcement` container, and the loader are unchanged — a v1.0 reader simply preserves unknown `kind`s on round-trip (below).

Forward-compat: unknown fields **and unknown `ReinforcingElement.kind`s** are preserved on round-trip; `rcfg_version` gates migrations. A reader must never drop a `kind` it doesn't understand (so a v1.0.x file with tendons survives a v1.0.0 load).

## 11. Tech Stack & Engineering Standards [REF-SYS-1100]

- **Frontend:** React 18 + TypeScript, Vite. State: Zustand. Styling: your choice (Tailwind suggested).
- **3D:** Three.js (+ `@react-three/fiber`, `drei`). Instanced meshes for bars; `TubeGeometry`/`CatmullRom` along centerlines.
- **Math:** small internal vector lib; `mathjs` for `len_expr`/`totalLengthExpr` evaluation in archetypes.
- **Export libs:** DXF writer, `pdf-lib`/`jspdf` for PDF, in-house BBS.
- **Engine:** pure TS package (`/packages/core`) with **no DOM/React imports**; ≥90% unit-test coverage on solver + validation (Vitest). Golden-file tests for BBS/DXF.
- **Manifest integrity (CI gate):** every `elements/`, `shapes/`, `schemes/`, `supplements/`, and code-pack file is validated at build time against a published **JSON Schema**, plus cross-reference checks — a scheme may only reference declared zones, existing shape ids, and catalogued supplements; archetype `len_expr`/`angle_expr` may only use in-scope symbols (§5.2.1f). This is what makes the "add JSON, no engine change" guarantee safe; broken manifests fail CI, not users.
- **Engineering-correctness gate (non-negotiable for a structural tool):** a suite of **hand-verified reference cases** per code pack (BAEL-FR, EC2) and the RPS overlay — known inputs → expected `As`, spacing, `l_s`/`l_bd`, tie limits, cut lengths — committed as golden tests and **signed off by a qualified structural engineer**. Engine math is not "done" until these pass; this sign-off (§14) is a release dependency, not just a coding task.
- **Hosting:** static build on a free tier (Cloudflare/GitHub/Netlify Pages). No server, no DB, no secrets in 1.0.
- **Performance budget:** solve+validate+redraw < 16 ms typical; export may block briefly with a spinner.
- **i18n:** FR/EN resource bundles.
- **1.1 service (later):** FastAPI + IfcOpenShell (IFC), Postgres (accounts/projects), object storage. Engine logic reused via a TS→service contract or a Python port of the geometry needed for IFC.
