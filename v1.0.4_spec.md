# RebarConfig v1.0.4 — Specification (façonnage flow hardening + addressable-bar completion)
### H1–H19 — bar-shaping (façonnage) correctness, the independent-bar capability gap, and editor robustness

**Status:** 🟡 **DRAFT — buildable specification, not yet implemented.** Authored 2026-07-03 (Zayd, Hetzner dev
box) from a deep code trace of the v1.0.3 façonnage flow (the F6 editor + the G2 addressable-bar channel), the
nine owner-validated concerns, and ten further points found in the trace. Grounded in the as-built v1.0.3 build
(`current_state.md`).

**Relationship to prior specs.** Extends `v1.0-Spec.md` (r3), `v1.0.1/.2/.3-Spec.md`. Still the **horizontal,
no-backend** track. v1.0.3 delivered the *machinery* (true geometry G1, the addressable `longBars[]` channel G2,
the F6 façonnage editor); v1.0.4 makes that machinery **correct, complete, and safe to drive** — it fixes silent
data loss and one crash, closes the independent-bar UI gap, and hardens the editor. **No new engine capability
except where noted (H2, H8);** most work is in the web adapter/UI, with two small, guarded core additions.

**Relationship to the logged v1.0.4 backlog** (`current_state.md §9`, 2026-07-01): the backlog's **item 1
(per-bar verification)** and **item 2 (lap-splice staggering)** are the *engineer-gated* deepenings. This spec is
the **non-gated hardening** that must land first (a broken/unsafe editor makes per-bar verification moot). **H5**
and **H14** are the seams where this spec hands off to those two backlog items; both are flagged **[ENGINEER-GATE]**
below and are scoped here only to the extent that needs no new code constant.

## 0. Why this increment + the invariants it must not break

Hands-on tracing of the v1.0.3 façonnage flow exposed that the editor and the addressable-bar channel accept
inputs they then **silently ignore or lose** (a "unique length" on any bent bar; a hook edit made while a field
is mid-invalid; a `.rcfg` import that changes params under a fixed shape), can **crash the solve** (changing one
bar's Ø on a shaped group), and expose only a **fraction of the capability the data model already supports** (the
independent-bar UI shows `u/v/Ø` only, though the model, adapter and engine already carry shape/façonnage/length/
axial/hooks). None of these need new engineering constants; all are correctness/UX debt on top of shipped seams.

**Hard invariants (do not violate).**
1. **Engine purity & data-driven** (v1.0 §2, §0.1). No React/three/DOM in `packages/core`; no new
   `if (elementType===…)` / `if (codePack===…)`. The two core touches (H2, H8) live in existing seams.
2. **Determinism.** Pure solver, byte-identical output for a given input.
3. **`cutLength` invariant (D-P1-1).** Preserved and, per **H3**, *strengthened* (positive-finite guard moves into
   the core generator so every consumer is protected, not just the editor).
4. **`.rcfg` forward-compat (NORMATIVE, v1.0 §10).** No schema change. All the fields this spec starts *using*
   (`AddressableBar.shapeId/faconnage/length/axialPos`, override params) already exist and already round-trip;
   v1.0.4 only makes the UI/adapter fill them correctly. A v1.0.3 file loads byte-identical.
5. **a11y parity.** Every new pointer action (independent-bar shape pick, extra-bar selection on the picker) has a
   keyboard/numeric equivalent.
6. **Golden discipline.** No BBS/cutLength golden may move for a *legacy* doc (DROITE groups, no overrides, no
   extras) — every fix here is gated on the presence of a non-default façonnage/override/extra. New behaviour is
   proven with new fixtures, not by re-baselining old goldens.
7. **Legacy byte-identical is the acceptance bar for every item.** Each item below states its "legacy no-op" proof.

**File map touched by this increment (reference).**
- UI: `apps/web/src/ui/FaconnageEditor.tsx`, `apps/web/src/ui/AddressableBars.tsx`, `apps/web/src/ui/Sidebar.tsx`,
  `apps/web/src/ui/SectionPicker.tsx`, `apps/web/src/i18n/strings.ts`.
- Adapter/store: `apps/web/src/engine/solveDoc.ts` (`faconnageParams`, `buildLongOverrides`, `buildExtraBars`,
  `releveExtraBars`), `apps/web/src/store/useStore.ts` (`withDoc`, `setExtraBars`, `setBarOverrides`).
- Doc types: `apps/web/src/engine/document.ts` (no shape change — semantics only).
- Core (guarded, minimal): `packages/core/src/geometry/segment-grammar.ts` (`generateBarShape`),
  `packages/core/src/pipeline/element.ts` (`buildLongBars`), plus the shape manifests in
  `apps/web/manifests/shapes/` (defaults + optional `totalLengthParam` hint).

## PART I — Correctness / crash / data-loss (must-fix)

## H1 — Per-bar override must inherit the group's façonnage params (crash fix)  [REF-SYS-1041]

### H1.1 The defect  (was C2 — highest severity)
`buildLongOverrides` (`solveDoc.ts:171`, called at `:265` for columns / `:346` for beams) is passed
`defaultParams = { L: geometry.H|L }` and the group's `shapeId`, but **never the group's own
`faconnage.shapeParams`**. Because the adapter always sets `shape: loadShape(shapeId)`, core `buildLongBars`
(`element.ts:318`) **always regenerates** an overridden bar. So an override that changes *only* Ø / length /
axial-pos — with no shape edit — regenerates the bar on the group's shape with `{ L: … }` params:
- **DROITE group:** harmless (`{L}` is the correct param set).
- **Any façonné group** (e.g. column longitudinal = BAIONNETTE with custom params): the regen params are missing
  `lower/crank/upper` → `evalExpr` throws inside `generateBarShape`. The throw propagates through
  `buildLongBars → solveElement → solveDoc → withDoc` (`useStore.ts:196`, **no try/catch**), out of the Zustand
  setter and the React event handler → **uncaught exception / crash**.
- **VERIFIED LIVE (prep P0.2, 2026-07-03):** a BAIONNETTE-façonné column + a Ø-only override on bar 0 throws
  **`expr eval failed for "lower": Undefined symbol lower`**; the same override on a DROITE group does not throw.
  H2 also verified: a BAIONNETTE `cutLength` is unchanged by an injected `L` (only DROITE reads `L`). See
  `apps/web/src/engine/faconnage_p02_verify.spec.ts` (a temporary probe asserting the *current* bug — its
  expectations flip when H1/H2 land).

### H1.2 Fix
1. **Root fix:** thread the group's *resolved* façonnage params as the override fallback. In `columnInput`/
   `beamInput`, compute `groupParams = faconnageParams(group.faconnage, { L: memberLen })` once and pass it as
   `buildLongOverrides(edits, { shapeId, diameter }, groupParams)`. An override with no `faconnage` then inherits
   the group's actual shape params (byte-identical to the group bar at the same Ø); an override with `faconnage`
   still wins. **This alone fixes the crash** — a Ø-only override regenerates the group's real shape at the new Ø.
2. **Skip regeneration only for geometry-neutral overrides (perf, optional):** an override that changes **only
   `axialPos` and/or `removed`** does not affect the centreline — omit `shape` so core keeps `g.shape`. **Ø and
   `length` DO affect the shape** (Ø drives `bendDeduction(angle,Ø)` + hook extension `≈10·Ø`, so `cutLength`
   changes; `length` drives the leg via H2) — these **must** regenerate, now from the group's params (fix #1). This
   is a compute optimization, not a correctness fix; fix #1 is what removes the throw.
3. **Defensive belt (store):** wrap `solveDoc(doc)` in `withDoc` (`useStore.ts:194`) in a try/catch that, on
   throw, **keeps the previous good `result`**, sets an error flag on the slice, and surfaces a non-blocking
   banner — so no future generator throw can ever white-screen the app. (General robustness, not a substitute
   for the root fix.) NB: the throw today is `evalExpr`'s "expr eval failed / did not evaluate to a finite number"
   (`expr.ts:46/50`) because `makeScope` does not default missing params to 0.

### H1.3 Testing
- Core/adapter: `bar_override_inherits_faconnage.spec` — a BAIONNETTE-façonné column, override one bar's **Ø only**
  → solve succeeds, the bar keeps the group's bent shape at the new Ø, `cutLength` matches the group bar's.
- Regression: overriding a DROITE-group bar's Ø stays byte-identical (existing `bar_overrides.spec`).
- Store: `store_solve_guard.spec` — force `solveDoc` to throw → the store keeps the last good `result` and sets
  the error flag (no unhandled rejection).

### H1.4 Deliverables
`solveDoc.ts` (group-param fallback + conditional `shape`), `useStore.ts` (guarded `withDoc`), two new specs, the
banner string in `strings.ts`. **Legacy no-op:** DROITE groups + Ø-only overrides unchanged.

## H2 — Unique `length` must have a defined meaning for every shape (not just DROITE)  [REF-SYS-1042]

### H2.1 The defect  (was C1)
`buildLongOverrides` (`:180`) and `buildExtraBars` (`:204`) inject `L: e.length`. Only `droite.json` has an `L`
param; `baionnette/releve/zbar/double_crank/stepped/crochet_l/u_bar/attente` do **not**. So a "unique length" set
on any bent bar is written to the doc, round-trips in `.rcfg`, and **changes nothing** in geometry or `cutLength`
— a silent no-op the user can't see.

### H2.2 Fix  [OWNER decision needed — see H2.5]
Define `length` as **"set the shape's principal straight leg so the fabricated `cutLength` equals `length`"**:
1. Add an optional `"totalLengthParam": "<key>"` hint to each open shape manifest naming the leg that `length`
   drives (DROITE→`L`, CROCHET_L→`a`, ATTENTE→`h`, BAIONNETTE→`lower`, RELEVE→`bottom`, Z_BAR→`run2`, …). One
   authored choice per shape, reviewed once.
2. In the adapter, map `length` onto that param **and solve for it** so `cutLength == length` (invert the linear
   `totalLengthExpr`: the named leg absorbs `length − (Σ other legs + hookAllowances − bendDeductions)`), instead
   of the current blind `L: length`. Clamp so the leg stays ≥ its manifest `min`; if `length` is too short to
   satisfy the fixed legs, reject (H3/H17 path) rather than emit a degenerate bar.
3. Where no `totalLengthParam` is authored, **disable/grey the length field** and label it "length is defined by
   the shape params" (no silent no-op).

### H2.3 Testing
- `unique_length_semantics.spec` — for each open shape, set `length = X` → generated `cutLength == X` (±0.01);
  a too-short `length` is rejected, not emitted.
- Legacy: DROITE `length` behaves exactly as today (the named param is `L`).

### H2.4 Deliverables
`totalLengthParam` hints in the 9 open-shape manifests, adapter leg-solver in `solveDoc.ts`, editor/`AddressableBars`
field enable/disable + label, spec. **Legacy no-op:** DROITE unchanged; a bent bar with no `length` set unchanged.

### H2.5 Owner decision
Confirm the "length ⇒ cutLength via the principal leg" semantic (vs. "length ⇒ overall envelope span"). The former
matches the BBS meaning of `l=` and is recommended.

## H3 — Move the `cutLength > 0` (positive-finite) guard into the core generator  [REF-SYS-1043]

### H3.1 The defect  (was A3)
`generateBarShape` only throws on `totalLengthExpr ≠ generated cutLength` (`segment-grammar.ts:248`). A param set
that makes **both agree at a ≤0 or non-finite value** passes core and is accepted by the schedule, splice and DXF;
only the editor rejects it (`FaconnageEditor.tsx:59`). The schedule can carry a degenerate bar the editor would
refuse.

### H3.2 Fix
Add to `generateBarShape`, immediately after the `cutLength` cross-check: throw if
`!Number.isFinite(cutLength) || cutLength <= 0` (message names the shape + params). Remove the now-duplicated
guard from `FaconnageEditor.tryGen` (it inherits core's throw via its existing try/catch). Every consumer
(`buildLongBars`, `spliceBar`, BBS, DXF) is now protected uniformly.

### H3.3 Testing
- Core: `cutlength_positive_guard.spec` — a params set yielding `cutLength ≤ 0` throws; a valid one is unchanged.
- Editor: existing `faconnage_editor.spec` invalid-rejection case still red-flags (now via the core throw).
- Regression: every existing shape golden green (no legit shape produces ≤0).

### H3.4 Deliverables
`segment-grammar.ts` guard, editor simplification, spec. **Legacy no-op:** all valid shapes unchanged.

## H4 — Editor buffer must resync on shape *and* member-length *and* committed-params change  [REF-SYS-1044]

### H4.1 The defect  (was A1)
`FaconnageEditor.tsx:54` resyncs the local `params` buffer only on `[shapeId]`. On a `.rcfg` import (same
`shapeId`, new `shapeParams`) or when H/L changes in the Geometry tab, `committed`/`memberLength` change but the
buffer doesn't — committing then freezes stale values and severs member-length coupling (the geometry↔façonnage
desync).

### H4.2 Fix
Resync on `[shapeId, memberLength, committedKey]` where `committedKey = JSON.stringify(faconnage?.shapeParams)`.
Guard against clobbering an in-progress *valid* local edit: only overwrite the buffer when the committed value
actually differs from the last value this editor committed (track a `lastCommittedRef`). This keeps live typing
intact while picking up external changes (import, geometry edit, bar re-selection).

### H4.3 Testing
- RTL `faconnage_resync.spec`: (a) change `memberLength` prop → DROITE `L` re-seeds to the new member length;
  (b) change `faconnage.shapeParams` prop (simulated import) → the fields update; (c) a mid-edit local value is
  not clobbered by an unrelated re-render.

### H4.4 Deliverables
`FaconnageEditor.tsx` effect rewrite, spec. **Legacy no-op:** no external change → identical behaviour.

## H5 — Removing a bar must reconcile the schedule count with As (or WARN)  [REF-SYS-1045]  [ENGINEER-GATE]

### H5.1 The defect  (was C7)
An override `removed:true` drops the bar from the render + BBS (`bbs.ts:192`), but the **count-group still drives
§7** so `As,prov` stays at the full count — the schedule now says fewer bars than the compliance verdict assumes.
For a *shape* change this "detailing add-on doesn't touch As" rule is defensible; for a *removal* it is a
correctness hazard (the drawing and the check disagree).

### H5.2 Fix  (scoped: no new code constant → not gated; the full per-bar As is gated)
- **Non-gated (this spec):** the `provided_area` check reads `layout.count` (`validation/index.ts:139`), which
  ignores `longBars`. When the addressable channel is active, recompute the **provided bar count per longitudinal
  zone** from `longBars` (excluding `removed`) and feed *that* count into `provided_area`, so removing/adding a bar
  moves `As,prov` by the real steel. Mixed-diameter weighting and per-bar `d` stay out (that is backlog item 1).
- **[ENGINEER-GATE] deferred to v1.0.4-eng / backlog item 1:** per-bar mixed-Ø `As` weighting + per-bar effective
  depth `d`. Until signed, a removal that also mixes diameters raises a WARN "As shown for the majority diameter —
  per-bar verification pending" (tiered model, never blocks export beyond today).

### H5.3 Testing
- `removal_reconciles_as.spec` — remove 1 of 6 identical bars → `As,prov` drops by one bar's area, the readout +
  export lock reflect it; same-Ø case is exact.
- Mixed-Ø removal raises the WARN, does not silently mis-state As.

### H5.4 Deliverables
`element.ts`/validation wiring to count from `longBars`, the WARN rule, spec + tests. **Legacy no-op:** no overrides
→ grouped count path unchanged (byte-identical §7).

## PART II — Capability gaps (the stated goal of the flow)

## H6 — Independent-bar UI must expose shape, façonnage, length, axial position & hooks  [REF-UI-1046]

### H6.1 The gap  (was B2 — the highest-leverage capability fix)
`AddressableBar` (`document.ts:83`), `buildExtraBars` (`solveDoc.ts:195`) and core `buildLongBars` (`element.ts:339`)
already carry `shapeId`, `faconnage` (shape params + hooks), `length`, `axialPos`. But `AddressableBars.tsx`
renders only `u/v/Ø` per row (`:110–118`) and `addExtra` hardcodes `shapeId:"DROITE"`, `length: memberLen`
(`:49`). From the UI every independent bar is therefore a straight, full-length bar. **Closing the gap is UI-only.**

### H6.2 Fix
Per independent-bar row (or an expandable editor for the selected extra), add: a **shape `<select>`** (the
`LONGITUDINAL_SHAPES` list), the reused **`FaconnageEditor`** (params + start/end hooks + live sketch + cutLength),
a **length** `NumberField` (honouring H2 semantics), and an **axial-position** `NumberField`. All write the
existing `AddressableBar` fields via `patchExtra`. `addExtra` keeps the DROITE default (sensible), but every field
is now editable. Reuse the same components as the override path so the two stay consistent.

### H6.3 Testing
- RTL `independent_bar_full_ui.spec` — add an extra, give it a RELEVE shape + hooks + length + axial pos → the doc's
  `extraBars[0]` carries all fields; the sketch renders; it appears in 3D placement + BBS with its own cutLength.
- Adapter: `independent_bars.spec` extended — a shaped/hooked/positioned extra flows through `buildExtraBars`.

### H6.4 Deliverables
`AddressableBars.tsx` extra-row editor, i18n strings (H18), spec + tests. **Legacy no-op:** an untouched extra is a
DROITE full-length bar exactly as today.

### H7.4 Deliverables

## H8 — Geometric validity for addressable bars: section bounds, axial bounds, clear spacing  [REF-SYS-1048]

### H8.1 The gap  (was C4 + C5)
`axialPos`/`length` range freely (UI `max=20000`) with no check that `axialPos + length ≤ member length` or that a
bar starts inside the concrete; extra-bar `u/v` range ±2000 with no clamp to the section and **no clear-spacing
check** against neighbours. A bar can be scheduled that physically leaves the element, or sits closer than a
vibrator can fit — exactly the "buildable?" rule the product sells — with no alert.

### H8.2 Fix  (tiered model — WARN/FAIL, in an existing validation seam)
Add pure predicates (core, data-driven, no element branch), consumed by the validator:
1. **axial-extent** — `axialPos + fabricated run > member length` (or `axialPos < 0`) → **FAIL** (un-buildable,
   blocks export).
2. **section-bounds** — an extra bar's `(u,v)` outside `[cover, dim−cover]` → **FAIL**.
3. **clear-spacing** — an override/extra bar within `< max(dg+5mm, Ø)` of a neighbour bar centre-to-face → **WARN**
   (reuses the existing clear-spacing helper; addressable bars are currently exempt).

### H8.3 Testing
- `addressable_validity.spec` — each predicate: an out-of-bounds axial/section bar FAILs + blocks export; a
  too-close extra WARNs; a valid bar passes.

### H8.4 Deliverables
Predicates + validator wiring in `packages/core`, alert strings, spec + tests. **Legacy no-op:** no
overrides/extras → no new items (existing goldens untouched).

## PART III — Robustness / consistency

## H9 — `pickShape` must run the validity guard before committing  [REF-UI-1049]

### H9.1 The defect  (was A2)
`editParam`/`setHook` gate commits behind `tryGen`; `pickShape` (`FaconnageEditor.tsx:71`) commits
`seedParams(...)` unconditionally — and seeds can be invalid for the chosen shape (H11). An invalid shape reaches
the store.

### H9.2 Fix
Run the seeded params through `tryGen`; commit only if it succeeds. On failure, keep the shape selected but show the
error and don't commit (or fall back to manifest defaults that are known valid — see H11).

### H9.3 Testing
- RTL `pickshape_guard.spec` — picking a shape whose positional seed is invalid does not commit an invalid shape;
  a valid pick commits.

### H9.4 Deliverables `FaconnageEditor.tsx`, spec. **Legacy no-op:** valid picks unchanged.

## H10 — A hook edit must not be silently dropped while a param is mid-invalid  [REF-UI-1050]

### H10.1 The defect  (was A4)
`hooks` is read from the committed store (`:48`) while `params` is the local buffer; `setHook` calls
`tryGen(params, nextHooks)` (`:91`) against the possibly-invalid buffer → throws → the hook change is swallowed
(the "unreachable" comment is wrong; it is reachable).

### H10.2 Fix
Validate a hook change against the **last valid params** (not the raw buffer). If the buffer is invalid, still
commit the hook against the last-valid params (hooks are independent of body legs) and keep surfacing the param
error; never swallow the hook edit.

### H10.3 Testing
- RTL `hook_not_dropped.spec` — make a param field invalid, then change a hook → the hook is committed; the param
  error stays shown.

### H10.4 Deliverables `FaconnageEditor.tsx`, spec.

## H11 — Manifest-driven seeds; drop the positional `i===0` total-length guess  [REF-DATA-1051]

### H11.1 The defect  (was A8 + the `seedParams` note)
`seedParams` (`FaconnageEditor.tsx:26`) seeds the first length param to `memberLength` and the rest to
`memberLength/6`. Correct only for DROITE; for `u_bar` it seeds `h = memberLength` (leg = full column height —
nonsense), and for shapes with no manifest `default` the seeds can be geometrically invalid (feeding H9).

### H11.2 Fix
1. Author a sensible `default` for **every** param in the 9 open-shape manifests (some already have them).
2. `seedParams` uses `p.default` for every key; only the shape's `totalLengthParam` (H2) tracks `memberLength`
   (and only for DROITE-like shapes where that is meaningful). No positional heuristic.
3. Guarantee the authored defaults produce a valid shape (a manifest-integrity test).

### H11.3 Testing
- `manifest_defaults_valid.spec` — for every open shape, `generateBarShape(shape, seedParams(...))` succeeds with
  `cutLength > 0`.
- RTL: picking each shape yields a valid initial sketch (no error state on first render).

### H11.4 Deliverables
Manifest `default`s, `seedParams` rewrite, integrity test, spec. **Legacy no-op:** DROITE seeds to member length as
today.

## H13 — One active code pack drives both the editor preview and the solve  [REF-SYS-1053]

### H13.1 The defect  (was A7)
`FaconnageEditor` imports a module-level `baelPack` (`:15`) and the **solve** is also hardwired to BAEL
(`solveDoc` defaults `code = baelPack`; the whole adapter is typed `BaelPack`). The EC2 pack exists but is
unreachable from the UI, contradicting the "code-pack agnostic" architecture (`core_logic §8`). Latent today; the
day EC2 is selectable the preview `cutLength` (mandrel/bend deductions differ) diverges from the solved one.

### H13.2 Fix  (scoped to remove the coupling, not to ship EC2 UI)
- Thread the **active pack** from the store (a single `activePack` selector) into both `solveDoc(doc, pack)` and
  the `FaconnageEditor` (prop, not import), so preview and solve are always the same pack.
- **Note (out of façonnage scope, flag separately):** actually wiring an EC2 picker + widening the adapter's
  `BaelPack` typing to the `CodePack` interface is a distinct line item; this spec only removes the double-source
  so it's *ready* for that.

### H13.3 Testing
- `active_pack_consistency.spec` — editor and `solveDoc` fed the same pack produce the same `cutLength` for a bar;
  swapping the pack changes both together.

### H13.4 Deliverables
`activePack` in the store, prop threading in `FaconnageEditor`/`solveDoc`, spec. **Legacy no-op:** default pack is
BAEL → identical numbers.

## H14 — Splices (G4) and façonnage overrides must compose predictably  [REF-SYS-1054]  [ENGINEER-GATE]

### H14.1 The defect  (was C8)
Splices are group-level, computed off `shape.cutLength` (`element.ts:400`). A bar given a unique length/shape via
the addressable channel is on the `longBars` path and is **not** spliced — so a 15 m unique bar won't auto-split
while its group-mates do.

### H14.2 Fix  (scoped: define + guard the interaction; per-bar splice math is gated)
- **Non-gated (this spec):** when a bar carries an override *and* the group has `autoSplice`/`splices`, either
  (a) apply `autoSplices` to the override bar's own `cutLength` too (so a long unique bar still splits), or
  (b) if per-bar splice is deferred, raise a WARN "unique-length bar not spliced — exceeds stock" when its run >

- **[ENGINEER-GATE] backlog item 2:** real staggered per-bar splices (the stagger fraction, esp. in critical

`buildLongBars`/adapter wiring for override auto-split, WARN string, spec. **Legacy no-op:** no override + no splice

## H15 — Stable, collision-free ids for independent bars  [REF-UI-1055]

### H15.1 The defect  (was C6)
`addExtra` builds `id: \`X${extras.length + 1}-…\`` (`AddressableBars.tsx:49`). Remove one from a 2-bar list, then
add → `length+1` reuses an existing id → React key collision + ambiguous override/selection targeting.

### H15.2 Fix
Generate ids from a monotonic per-doc counter (`extraSeq`, persisted on the doc so it survives round-trip) or a
deterministic max-existing+1. Never derive from `array.length`.

### H15.3 Testing
- `extra_bar_ids.spec` — add, remove, add again → ids are unique; selection/override targets the right bar.

### H15.4 Deliverables `AddressableBars.tsx` (+ a `extraSeq` counter), spec. **Legacy no-op:** existing ids preserved.

## PART IV — Polish

## H16 — Honour manifest `max`/`step` for length params  [REF-UI-1056]
**Defect (A5):** `FaconnageEditor.tsx:120–121` hardcodes `max=20000, step=10` for lengths; only `min` is honoured
(angle honours `max`). Latent (no manifest sets length `max`/`step` yet) but will be ignored the moment one does.
**Fix:** use `p.max ?? <fallback>` and `p.step ?? <fallback>` uniformly for both length and angle.
**Testing:** `numberfield_respects_manifest.spec` — a manifest length `max`/`step` is applied. **Deliverables:**
`FaconnageEditor.tsx`, spec. **Legacy no-op:** shapes with no `max`/`step` unchanged.

## H17 — Rich invalid feedback: real reason, last-valid sketch, `aria-invalid`  [REF-UI-1057]
**Defect (A9):** on error the editor shows a generic string (`:142`), renders no sketch (`:145`), discards the
thrown reason, and sets no `aria-invalid`. **Fix:** surface the thrown message (which names the failing leg/expr),
keep the last-valid sketch rendered but dimmed, and set `aria-invalid` on the offending field (track which key last
failed). **Testing:** RTL `invalid_feedback.spec` — an invalid edit shows the specific reason + keeps the prior
sketch + marks the field. **Deliverables:** `FaconnageEditor.tsx`, strings, spec.

## H18 — `AddressableBars` uses the i18n bundle, not inline `tr(fr,en)`  [REF-UI-1058]
**Defect (C9):** `AddressableBars.tsx` hardcodes bilingual literals via `tr(...)` while every other façonnage
surface uses the typed `strings.ts` bundle → drift. **Fix:** move all labels to `s.addressable.*` keys.
**Testing:** covered by the H6/H7 RTL specs (query by role/label). **Deliverables:** `strings.ts` keys,
`AddressableBars.tsx`, spec.

## H19 — Per-leg minimum > 0 to reject degenerate legs  [REF-DATA-1059]
**Defect (C10):** length `NumberField`s use `min = p.min ?? 0` and only the *total* `cutLength>0` is checked, so a
`baionnette` with `crank=0` or a `u_bar` with `w=0` passes but is degenerate. **Fix:** author a per-leg `min > 0`
in the open-shape manifests where a zero leg is meaningless; the editor honours it (H16). **Testing:**
`per_leg_min.spec` — a zero-leg edit is rejected at the field; the total guard (H3) remains the backstop.
**Deliverables:** manifest `min`s, spec. **Legacy no-op:** legs already ≥ their min unchanged.
