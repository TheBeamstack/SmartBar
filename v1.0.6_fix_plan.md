# v1.0.6_fix_plan.md — Correction & improvement plan (post-review of v1.0.5 + v1.0.6)

> **What this is.** The repair plan for the defects and gaps found by the adversarial review of
> **v1.0.5 (M1–M7)** and **v1.0.6 (N1–N6)** on **2026-07-11** (Zayd, Hetzner dev box). It is a *build
> contract*, in the same shape as the version specs: each phase has a defect, the evidence that it is
> real, the exact edits, the tests, a Definition-of-Done, and its risk to the goldens.
>
> **Why it exists.** v1.0.5 and v1.0.6 both ship **green** (`npm run check` → 830 tests / 152 files,
> re-run and confirmed). Every phase is internally correct and tested. The defects live **at the seams
> between phases** — each phase's tests only test that phase, so nothing failed. Three of the findings
> are *silent*: the app gives a confident answer that is wrong or inert, with no error.
>
> **Companions.** `v1.0.5_spec.md` (the requirements R1/R3 restore), `v1.0.6_spec.md` (the requirements
> R2/R5 restore), `current_state.md` §8 ledger (D-V105-*, D-V106-*), `owner_tasks.md` (people-gated items).
>
> **Plain-language summary for the owner.** Six things need fixing. One is *dangerous* (the app says
> "compliant" about a splice that is half as long as the code requires). One is *misleading* (on 6 of the
> 8 element types, steel you add is drawn and put on the schedule but never counted in the checks). One is
> *broken plumbing* (the new "place a bar by clicking" tool and the new "drag its end" tool were built by
> different phases and were never connected to each other). The rest are smaller. None of them require
> re-architecting anything — the seams are all where the architecture said they would be.

## 0. Invariants carried (unchanged — this plan must not break them)

All of `architecture_breakdown.md §2` still holds and is **not renegotiated** by this plan:

1. **Engine purity** — nothing in `packages/core` imports React/three/DOM.
2. **Determinism** — same input → byte-identical output.
3. **Everything structural is data** — no `if (elementType === …)` / `if (codePack === …)` in core.
4. **SI internally**, convert at the edge.
5. **Code-pack agnosticism** — validation calls named `code.*` functions.
6. **`.rcfg` forward-compat** — unknown fields/kinds preserved on round-trip.
7. **Every phase ends green** — `npm run check` + the new phase's tests; append a `current_state.md` §9 entry.

**One new invariant this plan adds** (it is the root cause of three findings):

8. **No silent inert edit.** A user action that appears to succeed must either change the document or
   report why it could not. A store action that finds no target must not return quietly. *(R2 enforces
   this for the placed-bar channel; R7 adds a guard test.)*

# R1 — Bundle equivalent-diameter reach (fixes F-A) `[v1.0.5 P-E]`

### The defect
`v1.0.5_spec` **P-E** requires: *"Equivalent diameter `φₙ = φ·√nᵦ` (≤ 55 mm) drives **cover**,
**clear-spacing-to-neighbours**, and **mandrel/lap rules**."*

As built, `code.bundleEquivDiameter` is called in **exactly one place** —
`packages/core/src/validation/placedBarRules.ts:111`, the `bundle_cover` check. **One of the four uses shipped.**

The reason is structural: `expandBundle` (`section/resolvePlacedBars.ts:221–229`) fans a `Bundle` into `n`
independent `SingleBar`s via `toSingle`, each carrying the **bare** `body.diameter`. Downstream,
`resolveSingleBar` (`:159`) calls `barSplice(shape, diameter, …)` → `code.l0({ diameter })`. The bundle's
identity is lost the moment it is expanded; nothing downstream can know it was one.

**This is not a provisional-constant problem.** The constant is right; the code passes the **wrong argument**.
No engineer sign-off will catch it — it will just ratify `l0()` and move on.

### The change

**1. Carry the equivalent diameter on the expanded bar (core).**
`types/placed-bar.ts` — add to `SingleBar` an optional, additive field:

```ts
/** v1.0.6-fix R1: for a bar expanded from a Bundle, the EQUIVALENT diameter φₙ = φ·√n (≤55) that the
 *  code rules (lap, mandrel, clear-spacing) must use in place of the bare Ø (EC2 §8.9 / BAEL; P-E).
 *  Absent on every non-bundled bar → byte-identical. */
equivDiameter?: number;
```

`expandBundle` sets it once, from the pack (never hard-code `φ·√n` — it is `code.bundleEquivDiameter`, a
pack-swappable rule; BAEL and EC2 must be free to differ):

```ts
function expandBundle(b: Bundle, ctx: ResolvePlacedContext): SingleBar[] {
  const n = Math.max(1, Math.round(b.n));
  const phiN = ctx.code.bundleEquivDiameter?.(b.diameter, n) ?? b.diameter;
  // …toSingle(…, { ...b, equivDiameter: phiN })
}
```
*(`expandBundle` currently takes no `ctx`; `expandPlaced` (`:255`) already has it — thread it through.)*

**2. Spend it where the spec says (core).** In `resolveSingleBar` (`:131–176`), introduce **one** derived
value and use it for the *code rules*, keeping the bare Ø for *geometry and mass*:

```ts
const diameter    = sb.diameter;                       // physical bar: area, mass, BBS Ø column
const codeDia     = sb.equivDiameter ?? sb.diameter;   // rule diameter: lap, mandrel, spacing
```
- **Lap (this phase, non-negotiable):** `barSplice(shape, codeDia, …)` → `code.l0({ diameter: codeDia })`.
- **Mandrel/bend (owner decision O-1 — see below):** `generateShape(…, codeDia, …)`.
- **Clear-spacing-to-neighbours (this phase):** `predicates.ts finishSpacing` already exempts intra-bundle
  pairs via `bundleId`; a **bundle-to-neighbour** pair must now be judged on `codeDia`, not the bare Ø.
  Thread `equivDiameter` onto `AddressableBarView` next to the existing `bundleId`.

**3. Keep the schedule physical.** The BBS must still list `n` real bars of the **bare** Ø with the real
mass — only the *rule* diameter changes. `computeBBS` reads `PlacedLongBar.diameter`, which stays bare.
Assert this explicitly (a bundle must not gain phantom mass).

### ⚠ Owner decision **O-1** — does `φₙ` drive the mandrel too?
Using `φₙ` for the **bend radius** changes the bar's `bendDeduction` → its **`cutLength`** → the BBS. For a
bundled bar only (no legacy doc has bundles → **no golden moves**), but it is a real geometry change, and the
mandrel model is already flagged provisional (**D-P1-2**, → G-BAEL).
- **Recommendation: yes, include it** — a 4×Ø20 bundle physically bends around a radius set by the group,
  not by one bar; a bundle bent on a bare-Ø mandrel is not fabricable. Ship it flagged PROVISIONAL, riding
  the existing G-BAEL/G-EC2 gate, and let the engineer ratify lap + mandrel together.
- If the owner defers it: ship **lap + clear-spacing only** in R1 and log the mandrel as an open item. The
  lap fix must not wait on this call.

### Tests — `tests/bundle_equiv_diameter.spec.ts` (new)
- `φₙ` is sourced from the **pack** (BAEL and EC2 both), never recomputed inline.
- **The headline case:** a 4×Ø20 bundle with a lap → `lapLength == l0(φₙ=40)`, and explicitly
  `!= l0(Ø=20)` — the exact assertion that would have caught this (`1323 → 2646`).
- A bundle whose lap now fails the anchorage/curtailment band **turns 🔴** (it should: a lap that was
  silently short is now honestly short until lengthened).
- **Mass/schedule invariant:** the BBS still schedules `n` bars at the **bare** Ø with unchanged unit mass.
- **`cutLength` invariant (D-P1-1)** holds for the bundled bar under the new mandrel (if O-1 = yes).
- A **non-bundled** bar is **byte-identical** (`equivDiameter` absent → same code path).

### DoD
`npm run check` green; no golden moved; `current_state` §8 gains **D-R1** recording that `φₙ` now drives
lap (+ mandrel, +spacing) and that the constants ride G-BAEL/EC2.

### Risk
**Low-medium.** Confined to bars expanded from a `Bundle` — a v1.0.5 feature with no legacy users. The one
real risk is the mandrel→`cutLength` coupling (guarded by the D-P1-1 cross-check, which *throws* on
disagreement — so a mistake here fails loudly, not silently).

# R2 — The placed-bar selection channel (fixes F-C) `[v1.0.6 U3/U4/U5]`

### The defect
Three phases built three halves of one feature and no phase owned the join:
- **N5** writes new steel to **`doc.placed`** (`useStore.ts:691–711 placeInSection`).
- **N2/N3** render every `standalone` resolved bar as a pickable square (`SectionPicker.tsx:40`) and route
  the click to `select({ kind: "extra", id })` (`useStore.ts:633–635 pickSectionExtra`).
- **N3's Inspector** resolves an `extra` against **`doc.extraBars`** (`Inspector.tsx:151`) — a *different
  array*. Miss → falls through to the empty-state hint.
- **N6's station actions** route through `patchSelectedBar` (`useStore.ts:365–383`), which handles
  `kind:"bar"` and `kind:"extra"` only; on a miss it `map`s the list to itself and commits an identical
  document → **silent no-op** (`elevation.ts:117–138 selectedBarStations` likewise returns `null`).

`current_state` flags this as *"row/bundle/layer curtailment awaits the N5 selection reaching the unified
`selection`"*. That understates it twice: it hits **every** placed bar **including a plain single**, and the
bars are not un-selectable — they are **selectable and inert**, which is worse.

### The change — one new selection kind, three consumers

**1. Store — the kind (`useStore.ts:97`).**
```ts
| { kind: "placed"; id: string }        // a bar in doc.placed (N5): single | row | bundle | layer
```
`select()` (`:605–620`) keeps the legacy highlight channels in sync exactly as the other kinds do
(reuse `selectedExtraId` for the 3D/2D highlight — the resolved bar's `groupId` **is** the placed id, so
the existing highlight path needs **no change**).

**2. Store — the router (`pickSectionExtra`, `:633`).** The picker cannot tell a legacy extra from a placed
bar; the store can. Resolve the id against the doc, once:
```ts
pickSectionExtra: (id) => {
  const doc = get().doc;
  const parentId = id.split("#")[0];                       // a row/bundle/layer member is `p1#2`
  const isPlaced = ((doc as {placed?: {id:string}[]}).placed ?? []).some((p) => p.id === parentId);
  get().select(isPlaced ? { kind: "placed", id: parentId } : { kind: "extra", id });
}
```
**Selecting a member of a row/bundle/layer selects its parent** — the object the user created and the
object they edit (spec U3: *"for a row: count/spacing/level; for a bundle: n"*). This is the single
decision that makes rows/bundles/layers first-class in the inspector for free.

**3. `patchSelectedBar` (`:365`) — the write path.** Add the `placed` branch, routing to `setPlaced`:
```ts
} else if (selection.kind === "placed") {
  const placed = (doc as {placed?: PlacedBarDoc[]}).placed ?? [];
  get().setPlaced(placed.map((p) => p.id === selection.id ? stripUndef({...p, ...patch}) as PlacedBarDoc : p));
}
```
Because every `PlacedBarDoc` variant extends the shared `PlacedBarBody` (shape/params/Ø/hooks/curtailment/
splices/removed), **all five N6 station actions light up for a row/bundle/layer with no further work** —
curtailing a row curtails all its bars, exactly as the model intends.

**4. `selectedBarStations` (`engine/elevation.ts:117`) — the read path.** Add the `placed` branch reading
the parent's body. It already returns the shape N6's handles and the inspector's numeric twins consume.

**5. `Inspector.tsx` — the `placed` branch.** Renders the parent object's fields:
- **all kinds:** Ø · shape (reused `FaconnageEditor`) · `<StationEditor/>` (curtailment/anchorage/splices —
  this is what makes N6 reach N5's steel) · remove;
- **single:** `u` / `v`;
- **row:** `count` ⊕ `spacing` · `extent` · `direction` · `skin` flag;
- **bundle:** `n` (stepper, floored 2–4);
- **layer:** `face` · `layerIndex` · `count` · `inset` · `span` · `layerGap`.
Reuse `Stepper` (N1) for counts and `NumberInput` for the rest — **no new control types.**

**6. Invariant 8 guard.** `patchSelectedBar` must **assert** it found its target (dev-time throw / store
`solveError` banner), so a future fourth channel cannot silently swallow edits again.

**7. Retire the duplication.** The `PlacedList` in `ToolPalette.tsx:144–204` (count/n + remove) becomes a
**selector list** — click a row → `select({kind:"placed"})` → the inspector owns editing. One editing
surface, per U3.

### Tests — `ui/placed_selection.spec.tsx` (new)
- Place a single → click it on the canvas → **the inspector shows its fields** (the exact case that fails today).
- Place a row → click any member (`p1#2`) → **the parent row** is selected; changing `count` re-solves.
- `curtailSelectedBar` / `addSelectedBarSplice` / `setSelectedBarAnchorage` on a placed bar **change
  `doc.placed`** and shorten the BBS cut length (the F-C assertions, inverted).
- A curtailed **row** curtails **all** its expanded bars.
- **Invariant 8:** a store action with a selection that matches nothing **does not commit an
  identical document** (it reports).
- Legacy `extraBars` selection still routes to `kind:"extra"` — **no regression** to N3's path.

### DoD
`check` green; the N5→N3→N6 chain composes end-to-end on column + beam; `current_state` §8 gains **D-R2**.

### Risk
**Low.** Purely additive in `apps/web`; no core, no `.rcfg`, no golden. The one thing to watch is that
`select()` keeps `selectedBars`/`selectedGroupIds`/`selectedExtraId` mutually exclusive (N3's §0.3.4
invariant) — covered by the existing `inspector.spec` assertions, which must stay green untouched.

# R3 — Placed steel feeds the checks on all 8 elements (fixes F-B) `[v1.0.5 P-B / V-A]`

### The defect
`v1.0.5_spec` **P-B** requires: *"The per-metre provided-area accounting (`slabProvidedPerMetre`) gains
these bands."* It did not. The four generic pipelines compute provided steel from the **native zone
parameters only**:
- `pipeline/slab.ts:80` · `stair.ts:90` · `joist.ts:81` → `slabProvidedPerMetre(z.diameter, z.spacing)` — spacing-driven;
- `pipeline/circular.ts:147` → `asProv: lz.count * barArea(lz.diameter)` — count-driven.

`input.placed` is resolved, rendered, scheduled and geometry-validated — and then **ignored by §7**. So an
engineer adds an extra top band over a support, watches it appear in the 3D, the coupe **and the BBS**, and
the verdict does not move: the element stays 🔴 and stays **export-blocked**. The tool tells them their own
steel does not exist.

*(The RECT path is correct — `element.ts` reconciles As/`d` over the real placed set via
`computeZoneGeometryWeighted`. R3 brings the other six up to it.)*

### The change

**1. Extract the credit rule, don't duplicate it.** RECT's zone-assignment logic (`element.ts:738–760`,
"a standalone bar reinforces the zone whose tension region it sits in") is the convention the owner already
ratified (2026-07-06). Lift the *shape* of it into a shared pure helper in `section/resolvePlacedBars.ts`
(where the placed-bar truth already lives):

```ts
/** Credit each resolved placed bar to a zone. `assign` is the SECTION's own convention (the one
 *  element-specific thing); the accounting is shared. No `if (elementType)` — the caller supplies it. */
export function creditPlacedToZones(
  longBars: PlacedLongBar[],
  assign: (bar: PlacedLongBar) => string | undefined,
): Map<string, { asProv: number; bars: PlacedLongBar[] }>
```

**2. Per-section assignment + accounting.**
- **CIRCULAR** (`circular.ts`): a placed bar credits the longitudinal zone → `asProv += barArea(Ø)`
  (or `n·A` for a bundle, already expanded). Straightforward — the zone is count-based, so this is exact.
- **SLAB / JOIST / STAIR**: the zone is **per-metre**, so a band must be converted. A `BarRow` of `count`
  bars over `extent` mm contributes **`asPerM = count · A_bar / (extent / 1000)`** to the zone it sits in;
  a lone `SingleBar` on a per-metre element contributes over its **tributary width** (the local bar
  spacing). Zone chosen by level: `v ≥ 0` → the TOP zone, `v < 0` → the BOTTOM/MAIN zone, matching the
  element's own zone `v`s. **⚠ This is an accounting convention, not a published rule → owner decision O-2.**
- **`d` (effective depth)**: recompute area-weighted across the native mat **+** the credited bars, exactly
  as RECT does — a placed band at a different level must move `d` or the credit is a half-truth.

**3. Spacing checks (V-A's deferred half).** `v1.0.5_spec` V-A is explicit that the RECT clear-spacing
metric **does not generalise**: *"a slab is judged per metre and a circular by arc spacing."* So:
- **SLAB/JOIST/STAIR:** feed the credited bars into the existing **per-metre spacing** profile check
  (a band that halves the local spacing must be seen).
- **CIRCULAR:** feed them into the existing **arc-spacing** check.
- Do **not** invent a unified spacing predicate (the spec logs that as out of scope — keep it out).

**4. Fix the snap gap that R3 exposes.** `placeInSection` (`useStore.ts:696`) passes **no `b`/`h`** for a
generic doc → `snapSection` cannot clamp to the cover envelope. Supply the section dims from
`elementSpecs`/`GenericDoc.geometry` (slab: `Ly × t`; circular: `D`) so a placed bar is clamped at the

# R5 — The drawing-board on all 8 elements (fixes F-D) `[v1.0.6 U1/U3/U4]`

### The defect
`v1.0.6_spec` U4 promises the tool + palette *"work on all 8 elements"*, and §9's definition of complete is
*"a tool palette places any shape/row/bundle/layer on **any of the 8 elements**; selecting anything opens a
contextual inspector."* As built:
- `SectionDock.tsx:25,79` renders `SectionCanvas` only when `isColumnDoc || isBeamDoc`;
- `Inspector.tsx:96` returns `null` for anything else.

On slab / two-way slab / joist / stair / circular column / pile there is **no canvas, no inspector, no
station editor** — only the palette and two numeric boxes with no visual frame. The *store action* works on
8 elements; the **drawing-board** works on 2. On six of eight, the user is still filling in a form — which is
the exact thing v1.0.6 set out to abolish.

### The change — generalise the canvas by section descriptor, not by element

The engine already dispatches by **section** (`RECT` / `CIRCULAR` / `SLAB`), never by element type
(**D-P3-1/D-P4a-2**). The UI must do the same. `SectionPicker` is **already 80 % there** — it reads
`result.member` and branches `envelope === "CIRCULAR"` vs rect (`SectionPicker.tsx:70–74`). What is missing
is not a rewrite; it is three seams:

1. **A pure `sectionFrame(result)` helper** (`apps/web/src/engine/sectionFrame.ts`, new, headless-tested) →
   `{ envelope, b?, h?, D?, cover, viewBox, clamp(u,v) }` — the **one** place the drawing frame and the
   cover-envelope clamp are derived, for every section:
   - **RECT** → the existing `b × h` box + rect clamp;
   - **CIRCULAR** → the disc + a **radial** clamp (`r ≤ D/2 − cover − Ø/2`) — today `snapSection`
     (`placement.ts:38–44`) silently *skips* the clamp when `b`/`h` are absent, which is why a pile bar can
     be typed outside the concrete;
   - **SLAB-family** → width × thickness (`Ly × t`), the same rect clamp at slab proportions.
2. **`SectionCanvas` un-gated** — drop `drawingFirst` (`SectionDock.tsx:25,79`); `SectionPicker` and
   `snapSection` both take their frame from `sectionFrame`. A slab's section becomes a wide, thin box with
   the mat's bars as dots — which is *exactly* what a detailer expects to see.
3. **`Inspector` un-gated** (`Inspector.tsx:96`) — the `placed` branch (R2) is already element-agnostic
   (it reads `doc.placed`). Keep the *legacy* `bar`/`extra`/`crosstie` branches column/beam-gated (those
   channels genuinely only exist there) and render the placed branch everywhere.

**Element-appropriate semantics (spec P-B) — honour them, don't flatten them:**
- **SLAB/JOIST:** the natural placed object is a **band** (a `BarRow` across the width) — default the palette
  to `add-row` on a slab, not `add-single`.
- **CIRCULAR:** P-B calls for a **pitch-circle addition** (an extra bar at an angular position) as well as a
  free interior `(u,v)` bar. Add an angular-placement affordance; the free `(u,v)` path already works.
- **STAIR:** free bars ride the waist frame — already handled by the shared pass.

### ⚠ Owner decision **O-3**
Snap-grid density per section family (5 mm is right for a column; a 2 m-wide slab wants coarser), and whether
a slab's palette should default to `add-row`. Both are UX-feel calls the headless gate cannot judge.

### Tests
- `engine/section_frame.spec.ts` (pure): frame + clamp per envelope; **a circular clamp is radial** (the
  bug today); a slab frame is width × thickness.
- `ui/drawing_board_all_elements.spec.tsx`: for **each of the 8** — the canvas mounts, a bar places at a
  clamped coordinate, clicking it opens the inspector, and a station edit reaches `doc.placed`
  (the R2 chain, on every element).
- The **a11y twin** (labelled button list + typed coordinate) is present on every section (invariant §0.3.3).

### DoD
`check` green; **owner GPU pass** on the six new canvases; **D-R5**; `v1.0.6_spec` §9 "complete" becomes
literally true.

### Risk
**Medium.** The largest phase, but it is `apps/web`-only and additive — no core, no `.rcfg`, no golden.
The real risk is *visual*: a slab section at true proportions is 20:1 and needs a sane aspect handling.
Budget the owner GPU pass accordingly.

# R9 — Two-way slab Y-direction credit (fixes / accepts F-H) `[v1.0.5 P-B]` — Review #2

### The defect
On a two-way slab the adapter (`solveDoc.ts:809 slabZoneV`) gives both bottom MAIN zones the same `v` and
both TOP zones the same `v`. R3's `creditPlacedPerMetre → nearestZone` breaks the tie "first zone wins" →
always the X zone. A placed bar's axis is always `Lx` (the placed model has **no span direction**), so the
credit landing on X is directionally *correct* (**not a wrong-green** — the deficient zone stays red). But the
**Y** zones (`As_main_y_bot`, `As_top_y`) can **never** be credited. **Reproduced:** placing a bottom band
raised `As_main_x_bot` 523.6→1654.6 and left `As_main_y_bot` at 523.6 (FAIL). So on E-SLB-02 a Y-direction
deficiency **cannot be fixed on the drawing board** — the steel is drawn + scheduled but uncounted (F-B's
symptom, ¼-live).

### ⚠ Owner decision **O-5** — make placed bands direction-aware, or accept + document the limit?
- **Accept (small):** log it honestly in `core_logic §6` and the UI (a placed band on a two-way slab reinforces
  the X span; use the native mat controls for Y) and add a guard test pinning the known behaviour. Cheapest,
  and never dangerous (stays conservative).
- **Fix (M):** give a `PlacedBarInput` an optional **span axis** (`"x" | "y"`), thread it into
  `resolvePlacedBars` (a Y bar runs along `Ly`) and `creditPlacedPerMetre` (assign by axis, not only by level).
  This is the real closure of P-B on a two-way slab; it touches the placed-bar type (additive/forward-compat),
  the slab pipeline, and the placement UI (a direction toggle). No golden moves (no legacy doc has placed bars).

### Tests
- If accepted: a guard test asserting the documented behaviour (X credited, Y not) so it cannot regress silently.
- If fixed: a Y-axis band raises `As_main_y_bot` and clears a Y-only deficiency; an X-axis band still credits X;
  `count ↔ spacing` equivalence holds per axis; legacy byte-identical.

### DoD
`check` green; **D-R9** in §8; `core_logic` / `current_state` state the true reach of "feeds As on all 8".

### Risk
**Low.** Additive; the accept path is documentation + a guard; the fix path is gated on new user content.
