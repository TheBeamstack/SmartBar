**Status:** 🟡 **DRAFT — buildable specification, not yet implemented.** Authored 2026-06-27 (Amer) from the
owner's seven directives, grounded in a code trace of the v1.0.1 build (see `current_state.md` D-V101-*).

**Relationship to v1.0 / v1.0.1.** This document **extends** `v1.0-Spec.md` (r3) and `v1.0.1-Spec.md`. It is

the more specific text here governs for these seven features.

## 0. Why this increment, and the invariants it must not break

v1.0.1 made the app **complete** (8 elements, projects, combined exports, ViewCube, coupe handle). Hands-on
use surfaced seven concrete gaps — three are **bugs/UX defects** (F2 cross-ties draw wrong; F3 readouts scroll
away; F7 bar binding is unusable), four are **capability gaps** (F1 no in-plane roll; F4 panels not arranged
for focus; F5 single spacing per member; F6 no user control of bar shape). v1.0.2 closes all seven.

**Hard invariants (do not violate).**
1. **Engine purity & data-driven (v1.0 §2, §0.1).** Nothing new in `packages/core` imports React/three/DOM.
   F2/F5/F6 are expressed as **data** (placement rules, transverse segments, shape manifests/params) +
   registered functions — never element branches.
2. **Determinism.** Same input → byte-identical solve/export (golden tests stay green).
3. **`.rcfg` forward-compat (NORMATIVE, v1.0 §10).** F2 (cross-tie bindings), F5 (region lists) and F6
   (per-bar `shapeId` + params + hooks) are **additive** persisted fields; older readers must preserve them on
   round-trip, and a v1.0.1 file (no such fields) must load unchanged (legacy defaults apply).
4. **`cutLength` invariant (D-P1-1).** Any user-shaped bar still has `cutLength = Σ schedule legs + Σ hookExt −
   Σ bendDeduction`, cross-checked against the shape's `totalLengthExpr` — the façonnage editor may not break
   fabrication lengths.
5. **a11y parity (v1.0 §8, §11).** Every new pointer interaction (drag-ring, 2D bar click, region drag) has a
   keyboard/numeric equivalent; the pointer path is an *addition*, never the only path.
6. **No structural-math change for F1/F3/F4/F7** (pure presentation/interaction). F2's "Auto (code)" rule and
   F5's seismic reconciliation lean on the **existing provisional RPS overlay** (gate **G-RPS**, unchanged) —
   v1.0.2 adds no new sign-off gate, but the auto cross-tie rule ships flagged `_provisional` like its overlay.

## 1. Feature F1 — In-plane view roll  [REF-SYS-811 / REF-UI-811]

### 1.1 Intent
The screen is the X–Y plane. There are three independent rotations: **around X** and **around Y** move the
model out of the plane (these are the orbit the ViewCube already does), and **around Z** (the view axis) is the
**in-plane roll** — the one currently missing. `OrbitControls` pins the camera up-vector to world-up, so the
view can never be rolled/tilted within the screen plane. F1 adds that third rotation.

### 1.2 Behaviour [OWNER ✓ drag-ring + roll buttons]
- **Roll-ring (free):** a thin curved arrow ring drawn around the ViewCube gizmo (top-right). Dragging it rolls
  the camera continuously around the current view direction (any angle).
- **Roll buttons (snap):** `↺` / `↻` controls in the ViewControls overlay roll by **±90°** per click, with
  a modifier (or long-press) for fine ±5° steps.
- **Home / named-view snaps reset roll to level** (up-vector returns to the element's natural up). Picking any
  of the 26 named views also re-levels the roll, so roll is a *temporary* adjustment on top of an orientation.
- **a11y:** the roll buttons are the keyboard path; the ring is the pointer addition (§invariant 5).

### 1.3 Architecture
Camera/interaction only — **no engine change**. Implementation note: `OrbitControls` cannot roll, so F1
either (a) maintains an explicit roll angle applied to `camera.up` after OrbitControls updates each frame, or
(b) swaps to a control that permits a free up-vector. Approach (a) is preferred (keeps orbit/zoom unchanged;
roll is a post-multiply). The roll angle lives in the store as **session state — NOT persisted in `.rcfg`**
(consistent with v1.0.1 §1.7 view state). A pure helper `rollUpVector(viewDir, rollRad) → up` is
headless-testable (the GPU ring/feel is verified on the owner's machine).

### 1.4 Acceptance
- A roll-ring + ↺/↻ buttons appear with the ViewCube; rolling tilts the whole scene within the screen plane.
- Orbit (X/Y) and zoom are unaffected; roll composes on top.
- Home and any named-view snap reset roll to level.
- Roll is reachable by keyboard (buttons) and is absent from every exported `.rcfg`.
- `rollUpVector` has headless unit tests; `npm run check` + `build:web` green.

## 2. Feature F2 — Column cross-ties (“brins”) rebuilt on real bar engagement  [REF-SYS-756 / REF-UI-756 / REF-DATA-756]

### 2.1 The defect (confirmed)
Today a column/beam tie carries a single `nLegs` number (2–6). `solveDoc.crossTieZones()` materialises
`(nLegs−2)/2` `EPINGLE` groups, but `placeBars`/`placeLoop` **centres each one at the section centre**, so they
render as floating bars in the middle of the section, one per cadre, engaging **no real bars**. The number, the
3D and the schedule do not correspond to a buildable cross-tie. `nLegs` also has no notion of *which* bars or
*which direction* (top↔bottom vs left↔right).

### 2.2 The model [OWNER ✓ replace the legs number + “Auto (code)” button]
A **cross-tie (épingle)** is a transverse bar that **engages two specific longitudinal bars on opposite faces**
and is placed **on the line between them** (its hooks wrap those bars), repeated up the member at the cadre
spacing (or per F5 region). The column transverse reinforcement becomes:
- the **perimeter cadre** (the existing closed `CADRE_RECT`), plus
- a **list of cross-ties**, each a `{ barA, barB, direction, diameter?, hookAngle? }` binding to two
  longitudinal bars (selected via the **F7 2D section picker**). Direction is inferred from the engaged faces
  (vertical = TOP↔BOTTOM, horizontal = LEFT↔RIGHT).

The raw **`nLegs` field is removed** from the column UI; `Asw` (which `nLegs` fed) is recomputed from the actual
leg count = perimeter (2 per crossed direction) + Σ cross-ties crossing that direction, so the Asw check stays
correct **and** matches what is drawn and scheduled.

### 2.3 Configuration UI [OWNER ✓ picker + per-direction presets + Auto]
- **Manual:** the F7 section picker — click an intermediate top bar then its facing bottom bar (or left/right)
  to drop a cross-tie; it renders in 3D at those bars' midpoint and gets a BBS mark.
- **Per-direction presets:** "engage every other intermediate bar, top↔bottom" / "…left↔right" buttons that
  populate cross-ties onto alternate intermediate bars automatically.
- **Auto (code):** one click engages **alternate longitudinal bars per the seismic detailing rule** (RPS-2011
  / EC8: every other bar, or each bar ≤150 mm from a restrained one) using the active **RPS overlay** — fully
  **user-overridable** afterward. The rule's spacing/engagement constants are `_provisional` (gate G-RPS).

### 2.4 Engine / data impact (within existing seams)
- Cross-ties are modelled exactly like the existing **`LINK_BAR_PAIR` supplements** (`resolveBarPairPlacement`
  already returns the midpoint + span). The fix is to make **`placeBars` honour a per-group anchor position**
  (place the épingle loop at the resolved `(u,v)` between the two bars, **not** centred) — a small change to the
  pure placement function, used by both 3D and the coupe engine.
- **Seismic engagement becomes real:** the cross-tie set feeds the actual `longBarsEngaged` count into the
  RPS overlay (today hardcoded to 4) so the `crosstie_engagement` check reflects the true configuration.
- **`.rcfg`:** the cross-tie list persists per element (additive; forward-compat). A legacy file with only
  `nLegs` migrates to an equivalent centred-pair set (or the perimeter-only cadre if `nLegs≤2`).
- **No element branching:** beams reuse the same model for their multi-leg stirrups.

### 2.5 Acceptance
- The column "Brins" number is gone; cross-ties are configured by picking bar pairs (or a preset/Auto).
- Each cross-tie renders **between the two engaged bars** (not centred), in 3D, the coupe, and the BBS, with a
  hook around each engaged bar.
- `Asw` and the leg count are derived from the actual cross-ties (number = model = schedule).
- "Auto (code)" engages alternate bars per the RPS overlay and is overridable; seismic `longBarsEngaged`
  reflects it.
- Legacy `.rcfg`/`nLegs` files migrate without data loss; `npm run check` green.

## 3. Feature F3 — Persistent per-zone verification readout  [REF-UI-820]

### 3.1 Intent
The config-dependent results (As,prov vs As,req, computed `d`, status) currently sit in `Badges` at the top of
the scrolling sidebar and **scroll out of view**, and show only one **aggregate**. The user must always see the
direct effect of each edit.

### 3.2 Behaviour [OWNER ✓ sticky per-zone bar atop the panel]
A **sticky readout bar pinned to the top of the controls column**, never scrolled away. It shows **one row per
reinforcement zone**:
- zone label,
- **As,prov vs As,req** with a pass/fail colour (green ≥ req, red < req), in cm²,
- computed **`d`** for that zone,
plus a single **overall status** chip (🟢/🟠/🔴) for the element. Multi-zone elements (beam: span / chapeau /
montage; slab: main / secondary / top; column: total) each get their row. The bar stays compact (collapses
to the aggregate line on very short panels) and updates in the same tick as every edit.

### 3.3 Architecture
UI-only — **no engine change**. The per-zone provided area + `d` already exist on `SolveResult`
(per-zone provided area, `ZoneGeometry.d`); F3 adds a pure selector `perZoneReadout(result, doc) → Row[]`
(headless-testable) and a `position: sticky` container. Works for all 8 elements via the zone list.

### 3.4 Acceptance
- The readout stays visible while the controls scroll; it lists every zone's As,prov/As,req (coloured) + d +
  overall status; values update live.
- Headless test for `perZoneReadout`; `npm run check` green.

## 4. Feature F4 — Workspace re-layout: Verification + Project + BBS as an expandable right column  [REF-UI-830]

### 4.1 Intent
"Verification" (the alerts/checks) and "Project" (the multi-element manager) live in different places today
(right strip vs bottom dock). The owner wants them — plus the BBS — as **one right-hand column**, each section
**independently scrollable**, that can **expand horizontally over the 3D** to focus.

### 4.2 Layout [OWNER ✓ Verif+Project+BBS right; Coupes bottom]
- The right column hosts three **stacked, collapsible, independently scrollable sections**, top→bottom:
  **Verification** (the alerts panel), **Project** (instance manager + steel takeoff), **BBS** (the schedule
  table). Each has its own scroll zone; the column has a header row to collapse/expand each section.
- **Expand control:** a toggle widens the whole right column leftward **over the 3D viewport** (e.g. to ~60%
  width) for focused reading, and restores. The 3D stays mounted (just narrower/occluded).
- **Bottom dock keeps only Coupes** (the 2D `sectionAt` preview + coupe manager), since it's spatially tied to
  the 3D.
- The navbar toggles (Coupes / BBS / Project / Vérifications) update to drive this arrangement: BBS/Project/
  Vérifications toggle their section in the right column; Coupes toggles the bottom dock.

### 4.3 Architecture
UI/layout only — **no engine change**. Restructure `App.tsx` (the `app-body` grid), move `ProjectPanel` and
`BbsPanel` into the right column alongside `AlertsPanel`, give each `overflow-y:auto`, and add an
`expandPanels` store flag driving the column width. `BottomPanel` keeps only `CoupePanel`.

### 4.4 Acceptance
- Right column shows Verification (top), Project, BBS, each scrollable + collapsible.
- An expand toggle widens the column over the 3D and restores it.
- Coupes remain in the bottom dock; all existing panel content/behaviour is preserved.
- `npm run check` + the RTL panel tests green.

## 5. Feature F5 — User-defined transverse regions (per-region cadre spacing)  [REF-SYS-757 / REF-DATA-757]

### 5.1 Intent
Stirrups/cadres are not uniformly spaced along a member — ends are typically denser than the middle. Today a
member has a single `{spacing}`. F5 lets the user define **regions along the length, each with its own cadre
spacing**.

### 5.2 Model [OWNER ✓ free region list]
A transverse group carries an **ordered list of regions**, each `{ from_mm, to_mm, spacing_mm }` covering the
member length 0..L (contiguous, no gaps/overlaps; the UI enforces and auto-fills the remainder). A single-region
list `[{0, L, s}]` is exactly today's behaviour (the migration default). The UI:
- a **region table** (add/remove rows; from→to + spacing each) with numeric entry, **and**
- an optional **drag** of region boundaries on the longitudinal elevation/3D (pointer addition; numeric stays
  the a11y baseline),
- a **"symmetric ends" quick-fill** (end-zone length + end spacing + middle spacing → three regions) as a
  convenience, since that's the common case.

### 5.3 Engine / data impact (transverse-segment seam)
- The engine already segments transverse steel for seismic (`END_BOTTOM/MIDDLE/END_TOP` with per-segment
  spacing). F5 generalises this to a **user region list** consumed by `transverseStations` (emit stations
  region-by-region), by `placeBars` (instance loops per region), and by the **BBS** (count cadres **per region**
  → correct totals).
- **Seismic reconciliation:** user regions are the base; when a seismic regime is set, the overlay's
  critical-zone spacing **tightens within the end regions** (takes the min) rather than replacing them, and the
  "symmetric ends" quick-fill can be **seeded from the seismic critical-zone length**. If a user region is
  looser than the code minimum in a critical zone → a WARN (not a silent override).
- **Exports:** the elevation *fiche* (PDF + DXF) shows a **per-region spacing callout** (`Ø8 e=100` / `e=200`)
  and the region boundaries; the BBS lists cadre counts per region (or merged with a region note).
- `.rcfg`: the region list persists (additive, forward-compat); a legacy single-spacing file → one region.
- Applies to members with transverse steel (columns, beams, circular/pile spirals as pitch-regions). **No
  element branching** — it's a property of the transverse group.

### 5.4 Acceptance
- A member can carry N regions with distinct spacings; 3D, coupe stations, BBS counts and the elevation
  callouts all reflect them per region.
- Regions are contiguous over 0..L (UI-enforced); the symmetric quick-fill and free table both work.
- Seismic tightens (not silently replaces) within end regions; a sub-code region warns.
- Legacy files migrate to one region; `npm run check` green.

## 6. Feature F6 — Façonnage editor: per-bar shape, parameters & hooks  [REF-SYS-520 / REF-UI-520 / REF-DATA-520]

### 6.1 Intent
Bars are not always straight: a longitudinal bar may be **hooked/cranked at its ends** (anchorage, joints
between elements) or **bent within its length** (bent-up *relevé*, cranked *baïonnette*, Z/stepped). Before we
can export a faithful **façonnage (bar-bending) table**, the user must be able to **define each bar's shape**.
The engine is already a full segment-grammar (straight, L, U, baïonnette, relevé, chapeau, hooks, mandrels,
`cutLength`); the gap is purely that each group's shape is hardcoded and its params auto-computed. F6 exposes
shape choice + parameters + end hooks to the user, per bar group.

### 6.2 Behaviour [OWNER ✓ catalog + params + end-hooks]
Per **longitudinal bar group**, a **façonnage editor**:
- a **shape picker** from a catalog (§6.3),
- **editable parameters** for the chosen shape (leg lengths, bend angles) seeded from the geometry (so it
  starts sensible) but freely overridable,
- a **start/end hook** control on every longitudinal group — **none / 90° / 135° / 180°** + hook length —
  independent of the base shape (the grammar's `endHooks` already supports this),
- a **live 2D façonnage sketch** (the same `generateBarShape → fiche` projection rendered as SVG), showing legs,
  bend angles, hooks, and the computed **cutLength**.
The chosen shape + params + hooks become the bar group's actual shape in the solve, the 3D, the coupe, and the
**BBS façonnage column** (the sketch + coded dimensions per scheduled bar).

### 6.3 Shape catalog [OWNER ✓ common + multi-bend]
Ship, as shape manifests (data — no engine change):
- **Common:** straight (`DROITE`), end-hook 90/135/180 (`CROCHET_L` + hook variants), L-bar, U-bar (`U_BAR`),
  cranked / lap-offset **baïonnette** (`BAIONNETTE`), bent-up **relevé** (`RELEVE`), starter/dowel (`ATTENTE`).
- **Multi-bend (new manifests):** **Z-bar**, **double-crank**, **stepped** (footing/step bars). Each is a new
  `shapes/*.json` segment-grammar entry registered in the shape registry — the §0.1 "new shape = new data"
  seam; no pipeline change.
- Closed transverse shapes (cadre, étrier, épingle, spiral, mesh) remain as-is; F2 governs cross-tie shaping.

### 6.4 Engine / data impact
- **Doc model:** each longitudinal group gains a user-editable `shapeId` + `shapeParams` + `hooks{start,end}`
  (today the column long bar is hardcoded `DROITE`, beam span `DROITE`, etc.). `solveDoc` passes these through
  instead of computing them, **keeping the engine generic** (it already accepts any shape+params).
- **Invariant (D-P1-1):** the editor must keep `cutLength = Σ legs + Σ hookExt − Σ bendDeduction` and the
  generator's `totalLengthExpr` cross-check — the UI surfaces a clear error if a custom param set is
  geometrically impossible (e.g. legs exceed the member). The integrity gate's expression-scope rules apply to
  the new manifests.
- **`.rcfg`:** `shapeId`/`shapeParams`/`hooks` persist (additive, forward-compat); a legacy file (no shape
  fields) uses the v1.0.1 default per group.
- **BBS/exports:** the façonnage table already has the `fiche` (legs/bends/hooks) — F6 renders the sketch +
  coded dims; the DXF/PDF bar marks (v1.0.1 fiche) reflect the real shape.

### 6.5 Acceptance
- Each longitudinal group can pick a catalog shape, edit its params, and set start/end hooks, with a live 2D
  sketch + cutLength; the choice flows to 3D, coupe, BBS, DXF/PDF.
- The new Z / double-crank / stepped shapes pass the manifest-integrity gate and generate valid cutLengths.
- Custom params that break the cutLength invariant are rejected with a clear message.
- Legacy files load with default shapes; `npm run check` (incl. integrity) + `build:web` green.

### 6.6 Deferred (flagged)
**Lap-splice / coupler scheduling between elements** (lap length, splice marks, stagger) is a larger feature —
**out of scope for v1.0.2**. F6 covers **end-shaping + hooks + bends on a single bar**; bar-to-bar splices
across elements are noted for a later increment unless the owner pulls them in (§9).

## 7. Feature F7 — 2D section picker & a usable bar-binding model  [REF-UI-555 / REF-SYS-555]

### 7.1 The defect (confirmed)
Supplement/cross-tie binding is by **raw integer index** typed into number fields, with **no way to see which
bar is which index** and **no 3D click wired** (`nearestBarIndex` exists but nothing calls it). It is unusable.

### 7.2 The mechanism [OWNER ✓ 2D section picker + presets]
A **live 2D cross-section diagram** (reusing the `sectionAt`/coupe projection) is the binding surface:
- every longitudinal bar is drawn as a **dot at its real `(u,v)`**, **numbered/labelled** (e.g. `T2` = 2nd top
  bar, or a running index) and coloured by face;
- **click a bar** to select it, **click a second** to **link them** (creates an épingle / cross-tie / the chosen
  supplement between them); selection **also highlights the bar in 3D** (and vice-versa — the 3D bars become
  clickable, raycasting to the same `nearestBarIndex`);
- **per-direction presets** (from F2) for quick "every other bar" engagement;
- the diagram replaces the raw `bar1/bar2` number fields for **all** binding (supplements **and** F2
  cross-ties), with a labelled list as the keyboard/a11y fallback (the same indices — parity preserved).

### 7.3 Architecture
Mostly **UI**; the binding model already exists (`nearestBarIndex`, `resolveBarPairPlacement`, indices stored
in `.rcfg`). F7 adds: a `SectionPicker` component (SVG bars from `result.bars` positions + faceTags), a stable
**bar-label scheme** (pure helper, headless-testable: position → `T2`/`B1`/`L1`…), 3D bar pickability
(raycast → index), and rewires `SupplementsPanel` + the new cross-tie UI onto it. Bindings still store **stable
indices** (never coordinates) so a layout change re-solves them (v1.0 §10). The supplement-rebind WARN flow is
unchanged (still keyed to a deleted index, now visible on the diagram).

### 7.4 Acceptance
- A 2D section diagram shows numbered, face-coloured bar dots; clicking two links them; selection syncs with 3D
  highlighting; 3D bars are clickable to the same effect.
- Supplements and F2 cross-ties are both bound through the picker; the labelled list is the keyboard fallback.
- Bindings persist as stable indices and survive layout edits (re-solve), with the existing rebind-WARN on a
  deleted reference.
- A headless test for the bar-label helper; `npm run check` green.

  tighten), `facade_shapes`/manifest-integrity for the new shapes + cutLength invariant, `bar_labels` +
  `section_picker` (RTL), plus the existing goldens stay green.
- **Engineering gates:** unchanged. F2 Auto-rule + F5 seismic reconciliation ride the existing **G-RPS**
  provisional overlay; no new sign-off gate.
