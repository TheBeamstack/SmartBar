# RebarConfig v1.0.1 — Specification (interactive-3D increment)
### ViewCube view-orientation widget · 3D coupe drag-handle + elevation cutting-line overlay

**Status:** Buildable specification for the **v1.0.1** horizontal increment. Scope is the two
**GPU/visual** features that v1.0 deliberately deferred (they need a real WebGL context + a human eye
to verify, so they could not be closed on the headless dev box — see `current_state.md` D-P6-2 and the
P5/P6 handoff "GPU / visual items not done"). Everything here is **camera/interaction only — no engine,
no `.rcfg` contract, no validation-math change** (the section geometry it manipulates is the *existing*
pure `sectionAt → CoupeView`, v1.0 §9.5).
**Date:** 2026-06-25
**Relationship to v1.0:** This document **extends** `v1.0-Spec.md` (r3). The features are already
*named* there — ViewCube at §2.1 / §8 [REF-SYS-810]/[REF-UI-810] + §14 item 18; the coupe drag-handle
at §8 ("**3D drag handle AND a numeric position/orientation field**") + §9.5 + [REF-EXT-GAP-7]. v1.0
shipped the **non-visual halves** (numeric + keyboard coupe placement with full a11y parity; the pure
`sectionAt` engine; the element→up-axis map as data). v1.0.1 adds the **direct-manipulation visual
halves**. Where this doc and v1.0 disagree, the more specific text here governs **for these two
features only**.
**Scaling model (unchanged):** horizontal — these are new *interaction* values on existing axes, not an
engine rewrite (v1.0 §0.2).

---

## 0. Why this is a separate increment

Two v1.0 features were specified and partially built but **could not be verified** on the headless
Linux dev box (no GPU): the camera **ViewCube** and the **in-viewport coupe manipulation** (a draggable
cut plane + its cutting-line drawn on the live 3D elevation). v1.0 shipped their *testable-headlessly*
substitutes so the product is fully usable without them:

- **Coupe placement already works** via numeric fields + a keyboard/list path (full a11y parity), and
  every coupe already previews live in 2D (`sectionAt` SVG) and drives the DXF/PDF cross-sections.
- **The camera** already orbits (OrbitControls) and the element→default-orientation map already exists
  as pure data.

v1.0.1 is therefore **pure additive polish on the 3D canvas**: it makes the camera and the coupes
**directly manipulable with the pointer**, matching the AutoCAD/Revit muscle memory the owner asked for,
**without removing** any existing numeric/keyboard path (which remains the accessibility baseline, §11).

**Hard invariants (do not violate).**
1. **No engine change.** `packages/core` purity (v1.0 §2, D-P2) is preserved — the ViewCube emits a
   camera quaternion; the drag-handle emits an updated `SectionCut` (`origin`/`normal`), both consumed by
   the *existing* pure functions. No new geometry/validation math.
2. **No `.rcfg` contract change.** Camera/view state is **session-only** (NOT persisted, v1.0 §8). The
   `SectionCut` shape is unchanged — the drag-handle just writes the same `origin`/`normal`/`lookBehind_mm`
   the numeric field already writes; coupes still round-trip via `section_cuts[]` (v1.0 §10).
3. **a11y parity is mandatory.** Every pointer-only action here has a pre-existing keyboard/numeric
   equivalent; the pointer path is an *addition*, never the *only* path (§11, same rule as supplement
   binding + the v1.0 coupe manager).
4. **Cosmetic conventions only.** Default iso angle, element→up-axis map, handle/cutting-line styling are
   **owner UX confirmations** ([REF-UI-810]/[REF-EXT-GAP-7], v1.0 §14 items 14–18) — **no structural-
   engineer sign-off** is involved.

## 1. Feature A — ViewCube view-orientation widget  [REF-SYS-810 / REF-UI-810]

### 1.1 Intent
An AutoCAD/Revit-style **cube gizmo** in a viewport corner that controls the **camera view direction**
(it orients the *view*, not the model). It gives a one-glance indication of the current orientation and a
one-click way to jump to standard views, plus free dragging for any angle. It supersedes the v1.0
placeholder where a beam was drawn "standing up" (D-P3-6) by making **element-aware orientation** the
default and giving the user full control thereafter.

### 1.2 Layout & anatomy
- **Position:** top-right corner overlay of the 3D viewport (configurable corner; default top-right).
  Fixed pixel size (~96–120 px), does not scale with the model, never intercepts orbit gestures outside
  its own hit area.
- **Cube faces (6):** `TOP / BOTTOM / FRONT / BACK / LEFT / RIGHT`, each labelled (FR/EN via the i18n
  bundle: *Haut/Bas/Avant/Arrière/Gauche/Droite*). Faces are the large click targets.
- **Cube edges (12) + corners (8):** smaller click targets that snap to the 12 edge-on views and the 8
  isometric corner views.
- **Compass ring (optional, v1.0.1 may template):** an N/E/S/W ring under the cube indicating plan
  heading; cosmetic.
- **Home control:** a small "house" affordance beside the cube → resets to the **element default**
  orientation (§1.4).
- **Projection toggle:** a separate **perspective ⇄ orthographic** control (button, not on the cube) —
  §1.5.

### 1.3 Interaction modes
1. **Snap (click).** Clicking a **face / edge / corner** animates the camera (eased, ~250–400 ms) to the
   corresponding orthogonal / edge / isometric view, **preserving the current zoom/target**. The set:
   6 orthogonal + 12 edge + 8 corner = **26 named view directions**.
2. **Free continuous rotation (drag).** **Dragging the cube** rotates the camera to **any orientation by
   any amount** (Revit-style), in lockstep with `OrbitControls`: dragging the cube and orbiting the scene
   are two handles on the **same** camera state — moving either updates the other so the cube always
   reflects the live camera. No snapping during a free drag; on release the orientation is kept as-is
   (it does **not** auto-snap to the nearest named view).
3. **Hover feedback.** The face/edge/corner under the pointer highlights to show the click target.

### 1.4 Element-aware default orientation
On element load (and on **Home**), the camera starts at a **3/4 isometric** angle with an **element-aware
up-axis**, reusing the **same element→up-axis map** the DXF/PDF elevation `fiche` uses (v1.0 §9.2 step 1,
[REF-SYS-810]) so the 3D and the drawings agree:

| Element family | Member axis attitude | Default camera |
|---|---|---|
| Column (rect / circular), pile | **member axis VERTICAL** (stands upright) | front-right-top 3/4 iso |
| Beam | **member axis HORIZONTAL** (lies along screen-x) | front-right-top 3/4 iso |
| Slab (1-/2-way), joist | **flat** (plane horizontal, thickness up) | top-biased 3/4 iso |
| Stair | primary span along screen-x, rake visible | front-right-top 3/4 iso |

This **fixes** the v1.0 placeholder (`rebarProps`/viewport drew the beam member-axis = +Y "standing
up", D-P3-6). The default angle + the up-axis map are **conventions** ([REF-UI-810], v1.0 §14 item 18) —
owner-confirmable, no sign-off. Proposed default iso = **front-right-top**.

### 1.5 Projection toggle (perspective ⇄ orthographic)
A control independent of the cube switches the camera between:
- **Perspective** (default) — natural depth, good for reading the 3D cage.
- **Orthographic** — true-to-scale parallel projection, for reading elevations/coupes without
  foreshortening. When orthographic + a snapped orthogonal view, the result is a clean 2D-like elevation.

Switching projection preserves view direction, target, and apparent framing (match the orthographic frustum
to the perspective fit so the model does not jump).

### 1.6 Accessibility (mandatory, §11)
The 26 named views are reachable **without a pointer**: a keyboard/list control (a `<select>` or a button
menu of named views: Top, Front, Iso NE, …) sets the same camera state the cube does, plus **Home** and the
projection toggle as buttons. Same no-pointer parity rule as supplement binding and the v1.0 coupe manager.
Cube and list stay in sync (both reflect/drive one camera state). Keyboard focus order: viewport → cube
(as a labelled group) → list fallback.

### 1.7 State & persistence
The current view (camera quaternion + projection mode) is **session state only** — held in the store, **NOT
written to `.rcfg`** (v1.0 §8). Reloading a project re-applies the **element default** (§1.4). (A future
1.0.x may add an optional per-project saved view; out of scope here to keep the `.rcfg` contract frozen.)

### 1.8 Architecture / implementation notes
- **Pure camera-state module (headless-testable).** A pure function layer maps *(element family → default
  quaternion)* and *(cube face/edge/corner → view direction)* and *(orbit delta ⇄ cube delta)*. This is
  unit-tested headlessly (no GPU) — e.g. "column default up-axis is vertical", "FRONT face → +Z look
  direction", "cube drag delta equals orbit azimuth/elevation delta". This mirrors how v1.0 unit-tests the
  pure `rebarProps`/`sectionAt` and keeps the GPU-only part minimal.
- **The widget itself** (React-Three-Fiber overlay or an HTML/CSS cube synced to the camera) consumes that
  pure module + drives `OrbitControls` (`makeDefault`), and is the **only** part that needs a browser to
  verify.
- **No new dependency required** in principle (a small bespoke cube), though a vetted drei `GizmoHelper`/
  `GizmoViewcube` may be used if it meets the snap-**and**-free-drag + a11y + projection-toggle requirements.

### 1.9 Acceptance (v1.0.1, Feature A)
- Cube renders in a viewport corner, labelled FR/EN, reflects the live camera at all times.
- Click face/edge/corner → camera snaps to the matching one of 26 named views (eased, zoom preserved).
- Drag cube → free continuous rotation locked to OrbitControls; orbiting the scene moves the cube too.
- New element / Home → element-aware 3/4 iso default (column upright, beam horizontal, slab flat).
- Perspective ⇄ orthographic toggle works and preserves framing.
- Named views + Home + projection reachable by keyboard/list (no-pointer parity).
- Pure camera-state module has headless unit tests; `npm run check` stays green; `build:web` ok.
- View state is **not** present in any exported `.rcfg`.

## 2. Feature B — 3D coupe drag-handle + elevation cutting-line overlay  [REF-EXT-GAP-7]

### 2.1 Intent
Let the user **place and move a section cut directly in the live 3D** with the pointer — a **drag handle**
on the cut plane — and see the matching **cutting-line + tag (A-A)** drawn on the longitudinal elevation in
the same 3D scene. This is the direct-manipulation counterpart to the v1.0 **numeric + keyboard** coupe
placement (which stays as the a11y baseline). The cut it manipulates is the **existing** `SectionCut`; the
slice it shows is the **existing** pure `sectionAt → CoupeView` (v1.0 §9.5) — already live-previewed in 2D.

### 2.2 The cutting-plane handle (in-viewport)
- **Visual:** the active cut is shown in 3D as a **translucent plane** (or a framed rectangle on the member
  envelope) at its `origin`, oriented by its `normal`, with a **grab handle** (a draggable disk/arrow gizmo
  at the plane centre) and a small **normal arrow** showing the viewing direction (+normal, the look-behind
  side, v1.0 §9.5.3).
- **Translate (v1.0.1 required):** dragging the handle **along the member axis** slides the cut to a new
  station; the 2D coupe preview + the elevation cutting-line update live. This is the pointer equivalent of
  the numeric **station** field. Constrained to the member length (0..length), with optional snapping to
  transverse-set stations (so a cut lands *on* a stirrup).
- **Re-orient / oblique (v1.0.1 target, may stage):** a rotation affordance tilts the `normal` for an
  **oblique** cut — the engine + `.rcfg` already support arbitrary `normal` (v1.0 §9.5, persisted); v1.0
  only lacked the on-canvas control. If the rotation gizmo slips, translate-only still satisfies the core
  ask (and oblique stays available numerically). State this honestly in the handoff if staged.
- **Look-behind:** a secondary affordance (or a drag along the normal) adjusts `lookBehind_mm`; defaults to
  the convention (≈ one transverse spacing, clamped 100–150 mm, v1.0 §14 item 15). Numeric field remains.
- **Multi-cut:** the manager lists cuts A-A, B-B, …; selecting one makes its handle active. The
  **auto-managed default representative coupe** (cuts[0], re-seeded each solve per D-P5-7) is shown but its
  station/orientation is owned by the engine until the user adds/edits an explicit cut.

### 2.3 Elevation cutting-line + tag overlay
For each cut, draw on the **live 3D longitudinal elevation** (and reuse the same geometry the DXF/PDF
elevation already draws, v1.0 §9.2/§9.5):
- A **cutting-line** (the standard symbol: a heavy dashed line with end ticks + direction arrows along the
  cut's trace on the elevation).
- A **tag** (`A-A`, auto-incrementing A, B, C…) at the line ends.
- The cutting-line style/tag is the **convention** from `[REF-EXT-GAP-7]` (lives in the code pack's
  `convention` module, owner-confirmable, v1.0 §14 item 14). Tags shown by default = §14 item 14.

This is the in-3D twin of the DXF cutting-line the v1.0 DXF-2 path already emits (`buildDxfCoupes`), so the
on-screen elevation and the exported drawing **agree by construction** (same `SectionCut`, same trace math).

### 2.4 Parity & data flow
- **Pointer → state:** the drag handle writes `updateCut(id, { origin, normal, lookBehind_mm })` — the
  **same** store action the numeric fields call. One source of truth (the store's `cuts[]`); the handle and
  the numeric panel are two editors of it.
- **State → views:** any cut edit re-runs the pure `sectionAt` (2D preview), redraws the 3D cutting-line,
  and (on export) the DXF/PDF coupe — unchanged from v1.0.
- **a11y:** the numeric **station / orientation / look-behind** fields + keyboard list (v1.0 coupe manager)
  remain the no-pointer path; the handle is additive (§11).

### 2.5 Architecture / implementation notes
- **No engine change.** The trace of a plane on the elevation, and the slice, are the **existing** pure
  core functions (`sectionAt`, and the elevation projection used by DXF). v1.0.1 adds only: a 3D gizmo
  (drag → `origin`/`normal`) and a 2D-in-3D overlay (line + tag) — both browser-only, both reading core
  output. The **station↔world mapping** (drag distance → `origin.y`) is a pure helper, headlessly testable.
- The gizmo may use a vetted R3F control (e.g. drei `<PivotControls>`/`<DragControls>`) constrained to the
  member axis, or a bespoke handle; it must not fight `OrbitControls` (modifier or explicit handle hit-area).

### 2.6 Acceptance (v1.0.1, Feature B)
- The active cut shows a translucent plane + grab handle + normal arrow in the 3D scene.
- Dragging the handle along the member axis moves the cut; the 2D `sectionAt` preview **and** the elevation
  cutting-line update live; the value matches what the numeric station field would set.
- The cutting-line + auto-incrementing tag (A-A, B-B…) render on the 3D elevation, styled per the
  convention module, and **match** the DXF-2 cutting-line for the same cut.
- (If shipped) the rotation affordance produces an oblique cut that round-trips through `.rcfg`
  (`origin`/`normal`); if staged out, oblique remains available via the numeric path and that is documented.
- Numeric + keyboard coupe placement still works unchanged (a11y parity).
- `updateCut` is the single write path; `npm run check` green; no `.rcfg`/engine contract change.

## 3. Out of scope for v1.0.1

- The remaining v1.0 P6 items not about these two features (engineer sign-offs G-BAEL/EC2/RPS/COUPE/TOL,
